# Designing and running an education program evaluation

**Goal:** a decision-ready answer to "is this programme working, for whom, and what
should we change or stop?" — proportionate to the programme's cost, and honest about
what the design can and cannot prove.

## 1. Draw the logic model first
Inputs → activities → outputs → short-term outcomes → long-term outcomes, plus the
**assumptions** linking each step. Example (reading intervention): tutors + materials →
3×30 min sessions/week → sessions delivered, attendance → decoding gains → reading
comprehension and course pass rates.
Weak links in the logic (e.g. "attendance will be high") are what you measure first.

## 2. Ask 3–5 evaluation questions, tied to decisions
- **Implementation:** was it delivered as designed (dosage, fidelity, reach — who got it)?
- **Outcomes:** did participants' outcomes change, and by how much?
- **Equity:** for which subgroups did it work or not?
- **Cost:** cost per participant / per outcome gained?
For each, write the decision it informs ("expand to Year 8?", "renew vendor contract?").
A question no one will act on is a question to drop.

## 3. Choose measures
- Outcome measures that match what the programme actually targets, are reliable, and are
  collected anyway where possible (assessments, attendance, credits, completions,
  employment for training programmes). Kirkpatrick's four levels (reaction, learning,
  behaviour, results) are a common frame for training — don't stop at level 1 surveys.
- Implementation data: session logs, attendance, observations against a short fidelity
  checklist. Without this you can't tell "it doesn't work" from "it wasn't done".
- Qualitative: a few interviews or focus groups explain *why* the numbers look as they do.

## 4. Pick the strongest feasible comparison
From weaker to stronger:
- **Pre/post only** — shows change, not cause (students grow anyway).
- **Comparison to similar non-participants** or to prior cohorts — better; check baseline
  equivalence and describe how groups differ.
- **Phased rollout or waitlist comparison** — often feasible and fair.
- **Randomised assignment** — strongest for cause; needs planning before launch.
Report effect sizes with the comparison, not just "scores went up". Be explicit in the
report about which claims the design supports.

## 5. Run the data-review cycle
- Set fixed review points (e.g. every 6 weeks for implementation data, end of term for
  outcomes). Same agenda each time: what does the data show → what might explain it →
  what will we try → who/when → how we'll know (a plan-do-study-act loop).
- Keep the improvement plan to a few actions with owners.
- Share results with the people delivering the programme first; they'll find errors and
  explanations you'll miss.

## 6. Report for the decision-maker
One page up front: questions, answers, confidence, recommendation, cost. Methods and
tables after. State limitations plainly (small n, attrition, non-random groups).

## Ethics and data
Consent/notice for surveys and interviews per local rules; de-identify data for analysis;
small-subgroup results can identify individuals — suppress cells below a threshold (often <10).

## Gotchas
- Measuring only what's easy (satisfaction) and calling it impact.
- Selection bias: volunteers and keen schools do better regardless.
- Uncertain: suppression thresholds and consent rules vary by jurisdiction and funder.

## Verify
- [ ] Logic model with assumptions written down.
- [ ] Each evaluation question names the decision it informs.
- [ ] Implementation fidelity measured alongside outcomes.
- [ ] Comparison approach stated, with claims matched to its strength.
- [ ] Review cycle produced dated actions with owners.
