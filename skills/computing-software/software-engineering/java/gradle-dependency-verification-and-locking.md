# Dependency verification and locking

## Gradle verification
```bash
./gradlew --write-verification-metadata sha256,pgp help     # creates gradle/verification-metadata.xml
./gradlew build --dependency-verification strict            # strict is the default once the file exists
```
The file lives at `gradle/verification-metadata.xml`; verification turns on as soon as it exists. It records checksums (and optionally trusted PGP keys) for artifacts and their metadata (POM, module files); plugins are verified too. Checksums prove integrity, signatures prove provenance; for the strongest protection use both. Bootstrapping trusts whatever the repositories serve right now, so review the generated file. Commit it and review diffs like code. Entries Gradle generated carry an `origin` starting with "Generated by Gradle": check them, then change `origin` to `Verified`.

To add a new version: bump it, rerun `--write-verification-metadata sha256` (use the same parameters every time; generation is incremental), read the diff, and delete entries for versions no longer used (Gradle never removes them). To export keys to a keyring file for faster verification use `--write-verification-metadata pgp,sha256 --export-keys`.

- Modes: `strict` (default), `lenient` (reports failures, build continues), `off`; set with `--dependency-verification` or `org.gradle.dependency.verification`.
- Use full 40-character fingerprints for `<pgp>` and `<trusted-key>` entries.
- `<trusted-artifacts>` means no verification at all for the matches; keep it narrow (for example your own group). SNAPSHOT (changing) dependencies and locally produced artifacts are not verified.
- Same artifact with different checksums in different repositories is often benign: verify, then record the extra value with `<also-trust>`.
- A failed checksum may mean a tampered artifact: investigate before accepting it. Gradle caches missing keys for 24 hours; `--refresh-keys` retries.

## Locking versions
```kotlin
dependencyLocking { lockAllConfigurations() }
// ./gradlew dependencies --write-locks   -> gradle.lockfile
```
Locking pins dynamic versions (`1.+`, ranges) so the resolved graph is reproducible. `lockAllConfigurations()` does not cover the buildscript classpath: activate it there with `resolutionStrategy.activateDependencyLocking()` (its file is `buildscript-gradle.lockfile`). Commit the lockfile. Do not combine locking with changing versions such as SNAPSHOT. Update selectively with `--update-locks group:name` (a trailing `*` wildcard is allowed). `LockMode.STRICT` also fails when a locked configuration has no lock state. Raising a direct dependency version above the locked one fails resolution until you update the lock state.

## Maven equivalents
Pin exact versions (no ranges) and manage them in a BOM. The Enforcer plugin has built-in rules for this: `requireUpperBoundDeps`, `banDuplicatePomDependencyVersions`, `dependencyConvergence`, `banDynamicVersions`, `requireReleaseDeps`, `requirePluginVersions`, and `requireFileChecksum` for a file with a known checksum. Rules take `level` (`ERROR` default, or `WARN`).

## Gotchas
- Locks and verification do not detect a malicious first-time dependency; combine with scanning and review of new dependencies.
- Gradle verification cannot discover dependencies resolved only at task execution time; add those entries by hand.

## Verify
Edit one checksum in the file locally; the build must fail with a "Dependency verification failed" message naming the artifact; revert.
