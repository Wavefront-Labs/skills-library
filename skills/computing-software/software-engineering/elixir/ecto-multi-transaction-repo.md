# Ecto.Multi and transactions

**Goal:** atomic multi-step writes with clear failure information.

```elixir
Ecto.Multi.new()
|> Ecto.Multi.insert(:user, User.changeset(%User{}, attrs))
|> Ecto.Multi.run(:welcome, fn _repo, %{user: u} -> send_welcome(u) end)   # must return {:ok, _} | {:error, _}
|> Ecto.Multi.update_all(:bump, from(s in Stats), inc: [users: 1])
|> Repo.transaction()
# {:ok, %{user: u, welcome: _, bump: _}} | {:error, failed_step, failed_value, changes_so_far}

Repo.insert(changeset, on_conflict: {:replace, [:name]}, conflict_target: :email)     # upsert
Repo.insert_all(User, rows, on_conflict: :nothing)
from(a in Account, where: a.id == ^id, lock: "FOR UPDATE") |> Repo.one()               # pessimistic lock
# optimistic: field :lock_version, :integer, default: 1 and Ecto.Changeset.optimistic_lock(cs, :lock_version)
```

## Rules
- All steps roll back together on any error. Side effects (emails, HTTP) inside transactions can happen before a later rollback; queue them after commit.
- `Repo.transaction/1` with a function: call `Repo.rollback(reason)` to abort; it returns `{:error, reason}`.
- Keep transactions short; they hold a pooled connection.
- `insert_all` bypasses changesets, autogenerated timestamps and callbacks; supply them yourself.

## Self-check
Make the second step fail and verify no row from the first step exists.
