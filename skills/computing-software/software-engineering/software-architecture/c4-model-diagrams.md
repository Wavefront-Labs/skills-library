# C4 model diagrams

Simon Brown's C4 model: hierarchical diagrams, like zoom levels on a map, built on a small set of abstractions.

## Abstractions
- **Person:** a human user role.
- **Software system:** the highest level of abstraction that delivers value; owned by one team; what you are building or interacting with.
- **Container:** a separately deployable/runnable unit that executes code or stores data - web app, SPA, mobile app, API service, database schema, message queue, serverless function, file store. (Not a Docker container necessarily.)
- **Component:** a grouping of related functionality behind an interface inside one container (not separately deployable).
- **Code:** classes/functions - usually generated by IDEs, rarely drawn by hand.

## The four levels
1. **System Context:** your system in the middle, people and external systems around it. Audience: everyone, including non-technical.
2. **Container:** zoom into your system - containers, their technology, and how they communicate. Audience: technical people inside and outside the team. The most valuable diagram for most teams.
3. **Component:** zoom into one container. Draw only when it adds value; it goes stale fastest.
4. **Code:** optional, generated.
Supplementary: system landscape (many systems in an enterprise), dynamic diagrams (numbered interactions for one scenario), deployment diagrams (containers mapped to infrastructure nodes per environment).

## Notation rules (from the C4 checklist)
- Every diagram has a title stating type and scope ("Container diagram for Internet Banking System").
- Every element has a name, type (`[Container: Java, Spring Boot]`), and a short description of its responsibility.
- Every relationship is a unidirectional arrow with a label describing intent ("Reads/writes customer data using JDBC"), plus technology/protocol for inter-container arrows.
- A key/legend explains shapes, colours, line styles. Acronyms explained.
- Don't mix levels of abstraction on one diagram.

## Common mistakes
- Drawing "microservice X" as a component instead of a container (or as a system when owned by your team - model each microservice as a container group, or as systems if separate teams own them).
- Showing message brokers as a hub with arrows to everything; instead label the arrows "publishes OrderPlaced to [Kafka topic orders]".
- Unlabelled arrows, or bidirectional arrows hiding which side initiates.
- Diagrams in a slide deck only; keep them as code next to the source (see diagrams-as-code skill).

## Verify
- [ ] Each diagram passes the C4 review checklist (title, key, element types, labelled arrows).
- [ ] A new joiner can explain the system's main data flows from the context and container diagrams alone.
