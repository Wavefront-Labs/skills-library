# Hide Delegate / Remove Middle Man

These two are inverses. Move between them as the code changes; neither is a final state.

## Hide Delegate
**Smell (message chain):** `manager = person.department.manager` - clients know that a person has a department and that departments have managers. If `Department` changes, every client changes.
```python
class Person:
    @property
    def manager(self): return self._department.manager   # delegating method
manager = person.manager
```
Mechanics:
1. For each method on the delegate the client uses, add a delegating method on the server.
2. Switch clients to the server method; test after each.
3. When no client needs the delegate, remove the server's accessor for it.

## Remove Middle Man
**Smell (middle man):** half of a class's methods just forward to another object; every new delegate feature needs another forwarding method.
Mechanics:
1. Add (or expose) a getter for the delegate.
2. For each client of a forwarding method, call the delegate directly; test.
3. Delete the forwarding methods once unused. IDEs: IntelliJ "Remove Middleman", Rider "Remove Delegating Members" for classes generated by delegation.

## Deciding
- Law of Demeter ("talk only to your immediate friends") argues for hiding, but blindly applying it produces fat facades of forwarders.
- Hide when the chain exposes structure clients should not depend on, or the delegate is likely to change.
- Remove the middle man when the server adds no meaning and forwarding grows with every delegate feature.
- Fluent builders and stream pipelines (`list.stream().map().filter()`) are chains by design, not the smell.

## Language helpers
Kotlin `class Foo(d: Bar) : Bar by d`, Lombok `@Delegate`, Python `__getattr__` forwarding (use sparingly: hides the API from type checkers).

## Verify
- [ ] Grep for the chain (`.department.manager`) returns no client hits after Hide Delegate.
- [ ] After Remove Middle Man, the class has no methods that only forward.
