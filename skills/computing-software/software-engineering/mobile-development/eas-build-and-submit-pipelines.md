# EAS Build and Submit

**Goal:** produce signed, installable binaries from a React Native/Expo project without maintaining
local Xcode/Gradle toolchains, and submit them to stores - reproducibly, per environment.

Expo Build compiles in the cloud: Android builds run on Linux runners hosted in Google Cloud
Platform, iOS builds on macOS runners in Expo's macOS cloud. `eas build --local` runs builds on your
own machine, useful for debugging or security policies that require local builds. Development builds
are shared across a team: when two members run `eas build:dev` and the project fingerprint matches,
the existing build is downloaded instead of rebuilt.

## eas.json profiles
Generated by `eas build:configure`, all build configuration lives under the `build` key. The
generated defaults:

```json
{
  "build": {
    "development": { "developmentClient": true, "distribution": "internal" },
    "preview":     { "distribution": "internal" },
    "production":  {}
  }
}
```
Profile names are arbitrary (they could be `foo`, `bar`, `baz`); these three are conventional:

| Profile | Audience | Shape |
|---|---|---|
| `development` | developers | `developmentClient: true` means the build depends on `expo-dev-client`; includes developer tools and is never submitted to a store. `distribution: "internal"` installs directly on devices. Add `"ios": { "simulator": true }` for the iOS Simulator (or use a separate profile, e.g. `development-simulator`). |
| `preview` | team/stakeholders | no developer tools, production-like, but either not store-signed (ad hoc or enterprise provisioning on iOS) or packaged non-optimally for stores (Android `.apk` recommended for preview, `.aab` for Google Play). |
| `production` | stores | submitted to a store (or TestFlight); installed through the stores. Cannot be installed directly on a device or emulator unless Android `"buildType": "apk"` is set; `.aab` is the recommended and default store format. |

Select with `eas build --profile <profile-name>`; with no `--profile`, EAS CLI uses `production` if
it exists.

## Fields that matter
Common options go at the profile root or inside `android`/`ios`; the platform-specific value takes
precedence. Fields shown in the official examples:
```json
{
  "build": {
    "preview": {
      "extends": "production",
      "distribution": "internal",
      "android": { "buildType": "apk", "gradleCommand": ":app:assembleRelease", "resourceClass": "medium" },
      "ios": { "simulator": false, "buildConfiguration": "Release" }
    }
  },
  "cli": { "requireCommit": true }
}
```
- `extends` inherits another profile; chaining is allowed up to a depth of 5, with no circular
  dependencies.
- `android.buildType`: `"apk"` is installable directly; the default store format is `.aab`.
  `gradleCommand` appears in the existing-React-Native-project example (`":app:assembleDebug"`,
  `":app:assembleRelease"`).
- `ios.simulator: true` builds for the simulator; `buildConfiguration` appears in the example as
  `"Debug"`; `image` selects the base image.
- `resourceClass` (`android.resourceClass`, `ios.resourceClass`): default is `medium`; `large` workers
  need a paid plan.
- `env` sets environment variables on the builder **and** is used to evaluate `app.config.js` locally
  when you run `eas build`, so build-time variants (bundle ids, names) can branch on it.
- `node` / `yarn` select tool versions. `withoutCredentials: true` appears on Android development
  profiles in the official examples.
- `cli.requireCommit` is part of the documented `cli` schema; check the Expo Build schema reference
  for its exact semantics before relying on it.

## Credentials
Expo Build can generate and manage Android keystores, iOS provisioning profiles and distribution
certificates, or use credentials you provide. A store-distributed app must be signed. Inspect and
manage credentials with `eas credentials`.
- Android: `eas build` signs with the keystore currently associated with the app. Keep the keystore
  private and out of the repository (debug keystores are the exception). With App Signing by Google
  Play, a lost upload keystore can be reset through Google Play support; under the older method a
  lost keystore could not be recovered.
- iOS: the three primary credentials are the distribution certificate, provisioning profiles and push
  notification keys. Provisioning profiles expire after 12 months, which does not affect apps in
  production; a new one is created at the next `eas build -p ios` or via `eas credentials`.
  `eas build:resign` re-signs an existing `.ipa` with a new ad hoc profile, for example to add a test
  device without rebuilding.
- `"distribution": "internal"` produces installable APKs on Android and ad hoc builds on iOS.

## Submit and automate
- `eas build --auto-submit` passes a successful build to Expo Submit using a submission profile with
  the same name as the build profile, or `--auto-submit-with-profile=<profile-name>`.
- Default auto-submit behaviour: iOS goes to TestFlight, not App Store review (promotion is manual);
  Android creates an internal release for new apps without enough metadata. Android `track` and
  `releaseStatus` in the submission profile control this: an explicit `track` also needs
  `releaseStatus` set to `completed`.
- `eas build:dev` builds or reuses a team development build when the fingerprint matches.
- EAS Update ties OTA JavaScript updates to builds through the profile's channel and the
  `runtimeVersion`: an update must be compatible with the build's native code, so native changes need
  a new build. Policies such as `appVersion` and `fingerprint` derive the runtime version; with
  `appVersion`, forgetting to bump the app version after a native change causes a mismatch.

## Failure modes
- **Build succeeds, installs nowhere** - `production` output is store-oriented (`.aab`). Use the
  `preview` profile or an explicit `buildType: "apk"` for direct installs.
- **Android upload rejected for signing** - the build was signed with a different keystore than the
  one the store expects for that app.
- **Update with new native code misbehaves** - `runtimeVersion` was not changed, so older builds
  accept an update that calls missing native code.
- **Variant config reads wrong values** - `env` in a build profile feeds `app.config.js` during
  `eas build`, so values may differ from a plain local `npx expo start`.

## Verify
- [ ] `eas build:configure` output reviewed; every profile's distribution and platform fields are
      deliberate rather than defaults inherited by accident.
- [ ] A preview build installs on a physical device from its URL.
- [ ] You know whether EAS or you own each credential, and the Android keystore is backed up.
- [ ] `--auto-submit` has been run once with a non-production submission profile before release day.
