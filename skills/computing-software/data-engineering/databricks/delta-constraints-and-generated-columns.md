# Delta constraints and generated columns

**Goal:** make the table itself reject bad rows and derive columns consistently, instead of trusting every writer.

## 1. Enforced constraints
```sql
ALTER TABLE prod.sales.orders ALTER COLUMN order_id SET NOT NULL;
ALTER TABLE prod.sales.orders ADD CONSTRAINT amount_non_negative CHECK (amount >= 0);
ALTER TABLE prod.sales.orders ADD CONSTRAINT valid_status CHECK (status IN ('NEW','PAID','SHIPPED','CANCELLED'));
SHOW TBLPROPERTIES prod.sales.orders;          -- constraints appear as delta.constraints.<name>
ALTER TABLE prod.sales.orders DROP CONSTRAINT valid_status;
```
- Adding a constraint scans existing data and fails if any row violates it — fix data first.
- A violating write fails the **whole transaction**, it does not drop rows. For "drop bad rows, keep going", use pipeline expectations or a quarantine table.

## 2. Generated columns
```sql
CREATE TABLE prod.events.clicks (
  event_id STRING, event_ts TIMESTAMP,
  event_date DATE GENERATED ALWAYS AS (CAST(event_ts AS DATE)),
  email STRING, email_domain STRING GENERATED ALWAYS AS (substring_index(email, '@', -1)))
PARTITIONED BY (event_date);
```
- Writers omit generated columns; if they supply a value it must equal the expression or the write fails.
- Partitioning by a generated date column lets filters on `event_ts` prune partitions automatically (Delta derives the partition filter) — for supported expressions such as CAST to DATE, `date_trunc` and the other expressions listed on the generated-columns page.
- Expressions must be deterministic; no UDFs or subqueries.
- On liquid-clustered tables you rarely need a derived partition column — cluster by `event_ts` directly.

## 3. Identity columns
```sql
CREATE TABLE prod.dim.customer (
  customer_sk BIGINT GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1),
  customer_id STRING, name STRING);
```
- Values are unique and increasing but **not contiguous** — gaps are normal.
- Declaring an identity column **disables concurrent transactions** on the table: parallel writers conflict. For high-concurrency or streaming fact loads, prefer a hash key (`xxhash64(business_key)`) or a UUID.
- `GENERATED BY DEFAULT AS IDENTITY` allows explicit values (useful for backfills/migrations).

## 4. Informational keys (Unity Catalog)
```sql
ALTER TABLE prod.dim.customer ADD CONSTRAINT customer_pk PRIMARY KEY (customer_sk) RELY;
ALTER TABLE prod.sales.orders ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer_sk) REFERENCES prod.dim.customer;
```
Not enforced. They document the model for BI tools and lineage; with `RELY` the optimizer may use the PK to eliminate joins/aggregations — only declare `RELY` when you test uniqueness elsewhere.

## Verify
- [ ] Inserting a violating row fails with a constraint error naming the constraint.
- [ ] A query filtering only on `event_ts` prunes `event_date` partitions (check files read in the query profile).
- [ ] Tables with identity columns have a single writer at a time.
- [ ] PK uniqueness is tested (dbt/expectations) wherever `RELY` is declared.
