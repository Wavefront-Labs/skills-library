# Choosing a transaction technique

| Scenario | Technique |
| --- | --- |
| Dependent writes | Nested writes |
| Independent writes | `$transaction([])`, batch operations |
| Read, modify, write | Interactive transactions (or idempotency, optimistic concurrency) |

Nested writes (see `prisma-client-nested-writes`) run in one transaction. Batch operations also run as transactions: `createMany`, `createManyAndReturn`, `updateMany`, `updateManyAndReturn`, `deleteMany`. Neither `updateMany` nor `deleteMany` supports nested writes, so a cascading delete of teams plus members cannot be done that way.

`$transaction([])` takes an array of queries and runs them sequentially in the listed order, all or nothing, returning results as an array:

```ts
const [posts, totalPosts] = await prisma.$transaction([
  prisma.post.findMany({ where: { title: { contains: "prisma" } } }),
  prisma.post.count(),
]);
```

Use it for batches of different record types, or to batch `$executeRaw` for things Prisma does not support. The classic case is a right-to-be-forgotten delete: `deleteMany` on posts, `deleteMany` on private messages and `delete` on the user, in one array.

It cannot pass ids between operations. If one write needs an id generated by another, use a nested write. If ids are precomputed (UUIDs generated up front), the writes become independent and either works, though the docs see no reason to switch from autoincrement ids and nested writes. Options such as `isolationLevel` go in the second argument.
