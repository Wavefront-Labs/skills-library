# Subject and authority key identifiers
Goal: chain builders pick the right issuer when several CA certs share a name.
RFC 5280 sections 4.2.1.1 and 4.2.1.2:
- The AKI identifies the public key matching the private key that signed the certificate, useful when an issuer has several signing keys (concurrent pairs or changeover). It can be based on the key identifier or on issuer name plus serial number.
- The `keyIdentifier` field of the AKI MUST be in all certificates generated by conforming CAs, to help path construction. The one exception: a self-signed CA certificate MAY omit it.
- The SKI MUST appear in all CA certificates (those with basicConstraints `cA` TRUE). In a CA certificate the SKI value MUST equal the AKI `keyIdentifier` of certificates that CA issues. Applications are not required to verify that key identifiers match during path validation.
- SKI for CA certificates SHOULD be derived from the public key. Two common methods: the 160-bit SHA-1 hash of the BIT STRING `subjectPublicKey` (excluding tag, length and unused-bits count), or a four-bit type field `0100` followed by the least significant 60 bits of that SHA-1 hash. Other unique methods are allowed.
- Where a key identifier was established before, the CA SHOULD reuse it. So a renewal on the same key keeps the same SKI.
- End-entity certificates SHOULD include an SKI, derived from the public key.
- Both extensions MUST be non-critical.
Verify:
- [ ] The SKI of each CA certificate equals the AKI `keyIdentifier` in the certificates it issued.
- [ ] Old and new CA certificates both build chains for the leaves they signed.
