# PAM stacks and control flags

**Goal:** predict exactly what a PAM config change does before applying it — PAM mistakes lock
out every login method at once.

## 1. Structure
`/etc/pam.d/<service>` (sshd, login, sudo, su, passwd …); each line:
`type  control  module.so  [args]`
- **types:** `auth` (who are you), `account` (are you allowed now: expiry, access rules),
  `password` (changing credentials), `session` (setup/teardown: limits, mkhomedir, logging).
- Shared stacks: RHEL `system-auth`/`password-auth` (generated by authselect); Debian
  `common-auth`, `common-account`, `common-password`, `common-session` (pam-auth-update).
- `@include common-auth` (Debian) / `auth include system-auth` / `substack` (like include,
  but `done`/`die` only end the substack).

## 2. Control flags
| Flag | Success | Failure |
|---|---|---|
| `required` | continue | remember failure, **continue** (result fail at end) |
| `requisite` | continue | **stop now**, fail |
| `sufficient` | **stop now, succeed** (if no earlier required failed) | ignore, continue |
| `optional` | only matters if it is the only module in the stack for that type (its result is used then) | same |
Bracket syntax gives full control: `[success=1 default=ignore]` = on success skip the next 1
line; `[default=die]` = fail immediately; `[success=ok new_authtok_reqd=ok ignore=ignore default=bad]`.
Order matters: modules run top-down.

## 3. Reading a real stack (Debian common-auth)
```
auth  [success=1 default=ignore]  pam_unix.so nullok   # password OK → skip pam_deny
auth  requisite                    pam_deny.so          # reached only on failure
auth  required                     pam_permit.so        # reached after a successful pam_unix
```

## 4. Changing it safely
- RHEL/Fedora: **use authselect**, never hand-edit generated files:
  `authselect current`, `authselect list-features sssd`, `authselect enable-feature with-mkhomedir`,
  custom profile: `authselect create-profile site -b sssd` (`-b` is `--base-on`), edit the new profile's
  templates, then `authselect select custom/site`.
- Debian/Ubuntu: the shared `common-*` files are generated by `pam-auth-update` (distribution tooling; see its manual page).
- Per-service tweaks go in that service's file (e.g. only `sshd` gets pam_access).
- **Keep a root shell open** in another session; test with a new login before closing it.

## Gotchas
- A typo in a module name = module fails to load → `required` fails for everyone.
- `sufficient` placed above a `required` account check bypasses that check.
- `nullok` on pam_unix allows empty passwords — remove on servers.
- With `UsePAM yes`, sshd runs PAM account and session processing for every authentication type, including keys.

## Verify
- [ ] The service's log shows no PAM module load errors.
- [ ] Password login, key login, sudo and su all still work for an admin test account.
- [ ] `authselect check` reports the configuration unmodified (RHEL).
