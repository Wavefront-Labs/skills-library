A crypt remote wraps another remote and encrypts before upload and decrypts after download. Content uses NaCl SecretBox (XSalsa20 plus Poly1305 for integrity). Accessing the wrapped remote directly bypasses encryption: downloads are scrambled and uploads are plaintext, so give the encrypted data a dedicated path and use only the crypt remote for it.

```ini
[secret]
type = crypt
remote = remote:path
password = ...
password2 = ...
```

## Choices at config time

- `remote`: any valid rclone path. A local path works for pure local encryption, for example on a USB drive. A string without `:` is a local relative path. For bucket backends wrap a bucket (`s3:bucket`); wrapping `s3:` with filename encryption encrypts the bucket name.
- `filename_encryption`: standard, a very simple obfuscation, or off, which only adds a `.bin` extension so the provider does not try to interpret content.
- `directory_name_encryption`: encrypt directory names or leave them intact (ignored if filename encryption is off).
- `password`: your own or generated (64 bits is memorable, 128 secure, 1024 maximum).
- `password2` (salt): optional but recommended, different from the password. Rclone stores no extra information on the remote, so a custom salt is effectively a second password you must remember. Omitted, a built-in salt is used.

## What is not encrypted

File length (computable to within 16 bytes) and modification time. The passwords in the config are only lightly obscured (AES-CTR with a static key), so use config encryption if the file could be exposed. With the same passwords and salt elsewhere you can re-create a compatible remote, although the obscured form differs.

Passwords generated by `rclone config` in 1.49.0 to 1.53.2 were insecure and should be changed (fixed in 1.53.3).
