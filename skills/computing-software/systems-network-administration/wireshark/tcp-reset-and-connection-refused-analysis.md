# TCP resets and refused connections

Find them: `tcp.flags.reset == 1` (a refused SYN shows as `[RST, ACK]`; a SYN retried at 1 s and 3 s showed as
`[TCP Retransmission]` in Wireshark 4.4.1); add a column for `ip.ttl` and `tcp.time_relative`.

## Classify
| Pattern | Meaning |
|---|---|
| SYN -> RST,ACK immediately | port closed on the host ("connection refused"), or a firewall rejecting |
| SYN -> nothing (SYN retransmissions with growing gaps) | silently dropped (firewall drop, routing), not refused |
| data -> RST from server | app aborted (crash, `SO_LINGER 0`, request too large, TLS failure) |
| RST after long idle | stateful device (firewall/NAT/LB) expired the flow, host replied to unknown session |
| RST mid-stream with odd TTL | injected by a middlebox (IPS, firewall, ISP), not the endpoint |
| FIN then RST | client closed while data still unread: normal for some browsers/apps |

## Who really sent it
- **TTL:** compare the RST's `ip.ttl` with the server's normal packets. Server SYN/ACK TTL 54,
  RST TTL 63 = generated by something a few hops closer (firewall).
- **IP ID** and window values inconsistent with the host's stream.
- **Timing:** an RST arriving faster than the server's normal RTT came from closer.
- **Sequence number:** an RST with sequence far off the expected value is ignored by the
  stack (and RFC 5961 section 3.2: an in-window RST that does not exactly match the expected sequence number draws a challenge ACK).
- Capture on both sides: an RST seen at the client but never sent by the server proves a middlebox.

## Idle timeouts
Compare `tcp.time_delta` before the failing request with firewall/NAT/LB idle timers
(often 300-3600 s). Fixes: TCP keepalives below the timeout, app heartbeats, or raising the device timer.
