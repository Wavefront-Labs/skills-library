# Building golden datasets for LLM evals

**Goal:** a versioned set of inputs with expected behaviour that tells you, on every change, whether the feature got better or worse.

## Define success first
Write measurable criteria per feature: "answers cite a source document", "extraction F1 meets a target you set per field", "refuses out-of-scope requests", "tone matches guide", "latency under your budget". Each criterion maps to a grader.

## Source the cases
1. **Production samples** (best): stratified random sample of real inputs by intent, length, language, customer tier. Scrub PII.
2. **Known failures:** every bug report and bad review becomes a case (regression tests).
3. **Edge and adversarial cases:** empty input, very long input, ambiguous requests, out-of-scope, prompt-injection attempts, multilingual, typos.
4. **Synthetic** cases generated by an LLM to fill coverage gaps - review them; they tend to be cleaner and easier than real traffic.

Start with a small set of well-chosen cases and grow it as the feature matures. Track coverage by tagging each case (intent, difficulty, risk category).

## Expected behaviour formats
| Task | Expected output form | Grader |
|---|---|---|
| Extraction, classification | exact values/labels | code (exact/normalised match) |
| Q&A over docs | reference answer + required facts + source IDs | fact checklist via LLM judge, citation check in code |
| Open-ended writing | rubric (must / must-not criteria) | LLM judge with rubric, human spot checks |
| Safety | expected action (answer / refuse / escalate) | code or judge |
Prefer checks code can verify; use judges for what code can't.

## Labelling quality
- Two annotators on a subset; measure agreement; resolve disagreements by refining the guideline, not by majority vote alone.
- Store the rationale for non-obvious expectations.

## Hygiene
- Version the dataset (in git or your eval platform's dataset feature) and record which version each eval run used.
- Keep few-shot examples and prompt-tuning examples out of the eval set (otherwise you test memorisation).
- Hold out a portion you look at rarely, to avoid overfitting prompts to the visible cases.
- Refresh with new production samples regularly; traffic drifts.

## Verify
- [ ] Success criteria written and each mapped to a grader.
- [ ] Case tags show coverage across intents and risk categories.
- [ ] Dataset version recorded with every eval result.
