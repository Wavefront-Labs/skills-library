# Server-side session storage

The browser holds only an opaque random session ID; session state lives on the server, so revocation is immediate
and data stays off the client. Follow the OWASP Session Management Cheat Sheet.

## Session ID
- Use the ID generated by your language or framework. If you must generate your own, use a CSPRNG with at least
  128 bits and make every ID unique. The cheat sheet's floor for any session ID is 64 bits of entropy; entropy, not
  length, provides the security, and the number of characters needed depends on the encoding (at least 16 hex
  characters for 64 bits).
- Exchange the ID in a cookie, not in a URL or other parameter; do not accept IDs submitted another way (this also
  helps against session fixation). URL-borne IDs leak through links, logs, history, the Referer header and search
  engines.
- Cookie attributes: `Secure` (mandatory), `HttpOnly`, `SameSite`, and no `Domain` attribute with a restrictive
  `Path`. The `__Host-` prefix requires `Secure`, no `Domain` and `Path=/`, prevents subdomain forgery and
  downgrade attacks, and is recommended for session IDs. Example:
  `Set-Cookie: __Host-SessionID=<value>; Secure; HttpOnly; SameSite=Strict; Path=/`.
- Never keep tokens in `localStorage` or `sessionStorage`: any script in the origin, such as through one XSS, can
  read them.

## Fixation and renewal
- Regenerate the session ID at login and whenever privilege changes; it is mandatory against session fixation. A
  strict mechanism accepts only IDs the application generated.
- Framework calls named by the cheat sheet include `session_regenerate_id(true)` (PHP) and `request.getSession(true)`
  with `HttpSession.invalidate()` (J2EE).
- An optional renewal timeout can replace the ID mid-session; keep the old ID valid only for a short safety interval.

## Store security
- Storing random tokens verbatim can be acceptable in a tightly controlled store, but anyone who can read it can
  reuse unexpired tokens. If read-only disclosure of the store (or its backups) is in your threat model, store a
  one-way verifier (hash) instead; this does not protect against stolen cookies or application compromise.
- Restrict access to the session store and encrypt backups and replicas at rest. Encrypt and protect the
  repository if it holds sensitive data.

## Timeouts
- Every session needs both an idle timeout and an absolute timeout, enforced server-side. Client-supplied time
  values can be manipulated.
- Cheat sheet ranges: idle 2-5 minutes for high-value applications, 15-30 minutes for low-risk ones; absolute depends
  on use, for example 4 to 8 hours for an office worker's full day.
- An idle timeout does not limit a hijacker who keeps the session active; the absolute timeout does.

## Revocation and visibility
- Logout must invalidate the server-side session. All IDs of the same logical session (rotations and IDs still
  accepted during a grace period) must be revoked together.
- Let users check active sessions, alert on concurrent logons, terminate sessions remotely, and keep a log of
  account activity (IP address, User-Agent, times).
- Log the session lifecycle (creation, renewal, destruction, privilege changes, timeouts, invalid activity) but never
  the raw ID; log a salted hash for correlation.
- Protect administrative interfaces that manage all active sessions.

## Verify
Logging out then replaying the old cookie returns unauthenticated; an idle session expires server-side at the
configured time; the session ID changes at login.
