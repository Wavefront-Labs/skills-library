# Service mesh mTLS (Istio and Linkerd)

## Istio: enforce
By default Istio configures destination workloads in `PERMISSIVE` mode, which accepts both plaintext and mutual TLS. To allow only mutual TLS, set `STRICT` in a `PeerAuthentication`:

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: foo        # one namespace; use istio-system for the whole mesh
spec:
  mtls:
    mode: STRICT
```

- Migrate namespace by namespace after clients are injected with the sidecar; a policy in the Istio system namespace (`istio-system` in the task) locks down all namespaces.
- Istio's Grafana dashboard shows which workloads still send plaintext to workloads in `PERMISSIVE` mode.
- After enabling `STRICT`, a plaintext client without a sidecar (the task's `legacy` namespace) fails to connect.
- If services cannot all be migrated, `PERMISSIVE` must stay, and then no authentication or authorization checks are performed for plaintext traffic by default; Istio recommends authorization policies for different paths.

## Istio: authorise by identity
`AuthorizationPolicy` supports CUSTOM, DENY and ALLOW actions, evaluated in that order. If no ALLOW policy applies to a workload the request is allowed; if any ALLOW policy matches it is allowed. The source `principals` field uses the form `TRUST_DOMAIN/ns/NAMESPACE/sa/SERVICE_ACCOUNT`, for example `cluster.local/ns/default/sa/productpage`, and rules can also match HTTP methods and paths:

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: {name: allow-sleep, namespace: default}
spec:
  action: ALLOW
  rules:
    - from:
        - source: {principals: ["cluster.local/ns/default/sa/sleep"]}
      to:
        - operation: {methods: ["GET"], paths: ["/info*"]}
```

## Linkerd: trust anchor and issuer
- Automatic mTLS uses a trust anchor plus an issuer certificate and private key. The trust anchor has limited validity: 365 days if generated by `linkerd install`, or a custom value if generated manually, so long-lived clusters must rotate it manually.
- The issuer certificate and key can also expire; cert-manager can automate their rotation.
- Rotate the trust anchor without downtime: read the current anchor from the `linkerd-identity-trust-roots` ConfigMap, generate a new anchor, bundle old and new, deploy the bundle (`linkerd upgrade --identity-trust-anchors-file` or the Helm `identityTrustAnchorsPEM` value), restart meshed workloads, rotate the issuer to one signed by the new anchor, restart again, then replace the bundle with the new anchor alone and restart again.
- `linkerd check --proxy` reports whether trust roots and the issuer certificate are within their validity period and valid for at least 60 days, and whether data plane proxies match the CA. If the trust anchor has already expired, use Linkerd's separate guide for replacing expired certificates.

## Verify
- [ ] A plaintext request from a pod without a sidecar to a `STRICT` namespace fails.
- [ ] An unlisted service account is denied by the AuthorizationPolicy.
- [ ] `linkerd check --proxy` shows no expiry warnings for trust roots or issuer.
