# Asymmetric key pair generation

SP 800-133 Rev. 2 section 5 says key pairs are generated by the key-pair owner or by a Trusted Party that
delivers them securely, and defers generation details to the algorithm standard (FIPS 186-5 for RSA, ECDSA and
EdDSA; FIPS 203/204/205 for ML-KEM, ML-DSA and SLH-DSA). In practice that means: let a
validated library or HSM do it, on the system that will use the private key,
and protect the private key from the first byte.

## Where to generate

- **On the device/HSM that uses it** (best): the private key never travels.
  CSRs carry only the public key out.
- **In a KMS/HSM** for server keys, signing keys and CA keys (non-exportable).
- **Centrally then distributed**: only when required (e.g. S/MIME key escrow);
  wrap it for transport (PKCS#12 with strong encryption, or KW/HPKE to the
  target) and destroy the central copy unless escrow is the point.

## Commands

```bash
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ec.key
openssl genpkey -algorithm ED25519 -out ed.key
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out rsa.key
openssl genpkey -algorithm ML-DSA-65 -out mldsa.key      # OpenSSL 3.5+ (fails with "unsupported" on 3.2)
chmod 600 *.key
```

## Pairwise consistency test (PCT)

FIPS 140-3 requires a PCT after generating a key pair: sign-and-verify (or
encrypt-and-decrypt / encaps-decaps) with the new pair before it is used
(gated: unconfirmed, the requirement is in ISO/IEC 19790 and the CMVP Implementation Guidance, not read here).
Validated modules do this internally. If you assemble a key from parts
(importing a private scalar, reading a seed), run your own PCT; it catches
corrupted keys and mismatched public/private halves before a CA certifies them.

## Seeds and determinism

- Ed25519, ML-KEM and ML-DSA private keys can be stored as a 32/64-byte seed.
  Storing the seed is compact, but whoever has it has the key; protect it the
  same way.
- Deriving key pairs deterministically from a master secret (HD wallets,
  `crypto_sign_seed_keypair`) is fine when the seed is a proper KDF output with
  a unique label per key; not from passwords.
- RSA key generation from a deterministic seed is non-standard across libraries;
  avoid it.

## Protect immediately

- Write private keys with mode 0600 (`umask 077` before generation), never into
  world-readable temp dirs or repo working copies.
- Encrypt at rest (`openssl pkey -aes256`, PKCS#8 with PBES2) or keep in a
  keystore/HSM.
- Record metadata: algorithm, creation date, purpose, owner, expiry.

## Verify

- [ ] Key generated on the system or HSM that uses it, or documented transport wrapping.
- [ ] PCT run for any key not generated by a validated module.
- [ ] Private key file permissions 0600 / non-exportable HSM attribute set.
- [ ] Algorithm and size match policy (see algorithm selection skill).
