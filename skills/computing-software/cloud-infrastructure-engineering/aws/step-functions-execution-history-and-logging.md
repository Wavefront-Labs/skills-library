# Step Functions execution history, logging and monitoring

**Goal:** answer "why did this execution fail and which step?" in a minute, and get told
about failures before users do.

## 1. Find and read failures (Standard)
```bash
aws stepfunctions list-executions --state-machine-arn "$SM" --status-filter FAILED --max-results 20
aws stepfunctions describe-execution --execution-arn "$EX" --query '{status:status,error:error,cause:cause}'
aws stepfunctions get-execution-history --execution-arn "$EX" --reverse-order --max-results 10 \
  --query 'events[].{id:id,type:type,state:stateEnteredEventDetails.name,err:taskFailedEventDetails.error,cause:taskFailedEventDetails.cause}'
```
The last `TaskFailed`/`ExecutionFailed` event names the error; walk back via
`previousEventId` to the `TaskStateEntered` for the input that caused it. History is kept 90
days after the execution closes; one execution can hold at most 25,000 events.

## 2. CloudWatch Logs (required for Express)
```bash
aws logs create-log-group --log-group-name /aws/vendedlogs/states/orders
aws stepfunctions update-state-machine --state-machine-arn "$SM" --logging-configuration \
 '{"level":"ERROR","includeExecutionData":true,"destinations":[{"cloudWatchLogsLogGroup":{"logGroupArn":"arn:aws:logs:<REGION>:<ACCOUNT_ID>:log-group:/aws/vendedlogs/states/orders:*"}}]}'
```
- Levels: `ALL` (every event type), `ERROR` (failures, timeouts and aborts of executions, tasks and states), `FATAL` (only execution failed, timed out or aborted) and `OFF`. Logs are billed at the CloudWatch vended logs rate, so `ALL` costs more than `ERROR`; delivery is best effort.
- `includeExecutionData: false` if payloads carry personal data.
- Use the `/aws/vendedlogs/states` prefix: without it each log group adds to the CloudWatch Logs resource policy, which has a 5,120 character limit (and an account limit of ten resource policies per Region).
- The execution role needs `logs:CreateLogDelivery`, `logs:CreateLogStream`, `logs:GetLogDelivery`, `logs:UpdateLogDelivery`, `logs:DeleteLogDelivery`, `logs:ListLogDeliveries`, `logs:PutLogEvents`, `logs:PutResourcePolicy`, `logs:DescribeResourcePolicies` and `logs:DescribeLogGroups`, with `Resource: "*"` (these actions do not support resource-level permissions).

Logs Insights:
```
fields @timestamp, execution_arn, type
| filter type in ["ExecutionFailed", "ExecutionAborted", "ExecutionTimedOut"]
| sort @timestamp desc | limit 50
```

## 3. X-Ray
Enable X-Ray tracing in the state machine's tracing configuration (the execution role then needs X-Ray permissions; roles generated by Workflow Studio include them) to trace states and downstream calls.

## 4. Metrics and alarms (namespace `AWS/States`, dimension `StateMachineArn`)
`ExecutionsFailed`, `ExecutionsTimedOut`, `ExecutionsAborted`, `ExecutionsSucceeded`, `ExecutionThrottled`,
`ExecutionTime` (ms), plus `ExecutionsRedriven` and `RedrivenExecutionsFailed`/`...Succeeded` for redrives. Version and alias dimensions exist for executions started through them. Metrics are best effort; use the `Sum` statistic for counts. Alarm on
`ExecutionsFailed > 0` for 1 datapoint with `TreatMissingData: notBreaching`.

## 5. Events
Standard workflows emit `Step Functions Execution Status Change` to the default EventBridge
bus — route `"status": ["FAILED","TIMED_OUT","ABORTED"]` to SNS/Slack with the execution ARN.

## Gotchas
- Express has no `get-execution-history`; without logging you only have metrics.
- Redrive (Standard) creates new events on the same execution; read history from the last
  `ExecutionRedriven` event.

## Verify
- [ ] A forced failure raises the alarm and the EventBridge notification within minutes.
- [ ] The CLI query in section 1 prints the failing state and error for that execution.
- [ ] Logs Insights query returns the failure from the vended log group.
