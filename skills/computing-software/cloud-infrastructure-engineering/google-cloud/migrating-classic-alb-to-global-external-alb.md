# Migrating classic ALB to global external ALB

Google recommends migrating classic Application Load Balancer resources to the global external
Application Load Balancer to get its advanced traffic management features. You migrate by changing
the load balancing scheme of backend services and forwarding rules from `EXTERNAL` to
`EXTERNAL_MANAGED`, after optionally testing a share of traffic on the new infrastructure.

## Identify
```bash
gcloud compute backend-services list --global --format="table(name,loadBalancingScheme)"
gcloud compute forwarding-rules list --global --format="table(name,IPAddress,loadBalancingScheme)"
```

## Order
1. All backend services attached to the forwarding rules.
2. All backend buckets (migrated at the forwarding-rule level; buckets have no load balancing scheme).
3. The forwarding rules, only after every attached backend service and bucket is migrated.

## Migration states (per backend service or bucket)
`PREPARE` -> optional `TEST_BY_PERCENTAGE` -> `TEST_ALL_TRAFFIC` -> change scheme to `EXTERNAL_MANAGED`.
After each step wait about six minutes. The resource must be in `TEST_ALL_TRAFFIC` before the
scheme change. In `TEST_BY_PERCENTAGE` and `TEST_ALL_TRAFFIC` the extra capabilities of the new
load balancer cannot be used; they become available after the scheme is `EXTERNAL_MANAGED`.
```bash
gcloud compute backend-services update web-be --global --external-managed-migration-state=PREPARE
gcloud compute backend-services update web-be --global --external-managed-migration-state=TEST_BY_PERCENTAGE \
  --external-managed-migration-testing-percentage=10
gcloud compute backend-services update web-be --global --external-managed-migration-state=TEST_ALL_TRAFFIC
gcloud compute backend-services update web-be --global --load-balancing-scheme=EXTERNAL_MANAGED
gcloud compute forwarding-rules update web-fr --global --load-balancing-scheme=EXTERNAL_MANAGED
```
Start with a small percentage, watch logs, and raise it gradually. Follow the "Migrate resources
from classic Application Load Balancer" page for the step-by-step procedure.

## Track and roll back
- Request header `X-External-Managed-Migration-Scheme-Override` (`EXTERNAL` or `EXTERNAL_MANAGED`) routes a request to a chosen fleet; `X-External-Managed-Migration-Selected-Scheme` reports which fleet served it.
- Rollback is possible within 90 days of changing the scheme. Remove new advanced traffic management features first, roll back the forwarding rules to `EXTERNAL`, then backend buckets and backend services (states back through `TEST_ALL_TRAFFIC`, `TEST_BY_PERCENTAGE`, `PREPARE`). Rolling back a backend service requires rolling back the forwarding rule.

## Differences to check
- Not supported on the global external ALB: Standard Network Tier and the GKE Ingress controller (use the GKE Gateway controller).
- Status codes: all backends unhealthy, banned cipher and early upstream reset return 503 (classic: 502); failed connection upgrade 403 (classic 400); oversized header 431 (classic 413).
- Headers: `X-Forwarded-For` uses `,` with no space; header keys are lowercased; repeated headers may be combined.
- Request handling: backslashes converted to forward slashes, duplicate slashes merged, `#` in the path returns 400.
- URL map host matching considers the port number as well as the hostname.
- Expect more backend connections (especially HTTP/1.1) and monitor backend memory.
- Session affinity is disturbed while a percentage is being tested; the scheme change invalidates cookies generated by the classic fleet.

## Verify
- [ ] Error rate and latency unchanged at `TEST_ALL_TRAFFIC`; the forwarding rule shows `EXTERNAL_MANAGED`.
