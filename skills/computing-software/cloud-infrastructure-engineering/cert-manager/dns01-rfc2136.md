Solver fields under `spec.acme.solvers[].dns01.rfc2136`:
- `nameserver`: authoritative server, e.g. `1.2.3.4:53`
- `tsigKeyName`: the key name used with `dnssec-keygen`
- `tsigAlgorithm`: must match the keygen algorithm, e.g. `HMACSHA512`
- `tsigSecretSecretRef.name` / `.key`: the Kubernetes Secret and the key inside it (not the key value)

BIND setup: enable dynamic updates per zone manually, then generate the key: `dnssec-keygen -r /dev/urandom -a HMAC-SHA512 -b 512 -n HOST example-com-secret`. Test with `nsupdate -k <keyID>`: add a TXT record, `send`, check with `nslookup`, delete, `send`, check again. Any `nsupdate` failure will also break cert-manager.

Create the Secret in the cert-manager namespace from the `.private` file's key string: `kubectl -n cert-manager create secret generic tsig-secret --from-literal=tsig-secret-key=<secret>`.

Behaviour and tips:
- cert-manager waits until all authoritative nameservers agree before contacting Let's Encrypt, to avoid rate-limit lockouts. Debug against ACME staging first.
- The TSIG key may need double base64 encoding; `nsupdate` testing reveals this.
- Lower the zone refresh time to about five minutes for first issuance; the whole flow can take about five minutes.
- Run `nsupdate` from a pod in the same namespace to rule out firewalls.
- Add `--v=5` to the cert-manager container for detailed logs.
- Configuration alone does nothing until a Certificate is requested.
