# Workload immutable fields: the "field is immutable" error, by object

**Goal:** stop re-running a failing `kubectl apply` against a validation error you cannot patch
through, and know the escape hatch for each immutable field, which differs by object kind.
The tables below follow the update validation in the Kubernetes source on main (v1.38
development; latest release v1.37.1); confirm against your cluster's version.

## 1. Field-by-field
| Object | Immutable field | Workaround |
|---|---|---|
| Deployment, ReplicaSet, DaemonSet, StatefulSet, Job | `spec.selector` | create a replacement object (a Deployment can be deleted and recreated, with `--cascade=orphan` to keep running Pods) |
| StatefulSet | `spec.volumeClaimTemplates` | `kubectl delete sts <name> --cascade=orphan`, re-apply with the new template; existing PVCs are not rewritten |
| StatefulSet | `spec.serviceName` | recreate the StatefulSet |
| Job | `spec.template` | delete and recreate the Job; exception: scheduling directives of a suspended Job can be changed (see the Job docs) |
| Job | `completionMode`, `podFailurePolicy`, `backoffLimitPerIndex`, `managedBy`, `successPolicy` | recreate the Job |
| Job | `completions` immutable for non-indexed Jobs; mutable for Indexed Jobs (elastic Indexed Jobs) | recreate, or use an Indexed Job |
| Pod (direct) | everything except `spec.containers[*].image`, `spec.initContainers[*].image`, `spec.activeDeadlineSeconds` (set once or only decreased), `spec.terminationGracePeriodSeconds`, `spec.tolerations` (add only), `spec.schedulingGates` | delete and let the owning controller recreate it; resources via the `resize` subresource, ephemeral containers via their subresource |

Job `parallelism` is not in the immutable list. For the Deployment selector the docs add:
it cannot be updated via `kubectl patch`, `edit`, `apply` or `helm upgrade`; narrowing needs
matching Pod template labels; changing a value or adding a key orphans the old ReplicaSet and
creates a new one; removing a key is an overlapping change that orphans nothing.

## 2. `kubectl apply` vs `replace --force`
- `kubectl apply` sends a patch; against an immutable field it fails with the same validation
  error as any other client.
- `kubectl replace --force` deletes and then recreates the resource (the Quick Reference shows
  `kubectl replace --force -f ./pod.json`). Suitable for Jobs and Pods you can lose; for a
  StatefulSet delete with `--cascade=orphan` first if its Pods and PVCs must survive.
- GitOps tools hitting an immutable-field diff show the resource out of sync until the
  resource is recreated or given a new name.

## 3. pod-template-hash
The Deployment controller adds a `pod-template-hash` label to every ReplicaSet it creates or
adopts (generated by hashing the ReplicaSet's `PodTemplate`), and the value is added to the
ReplicaSet selector, the Pod template labels and any existing Pods the ReplicaSet has. This
ensures child ReplicaSets of a Deployment do not overlap, which is why the Deployment's own
selector can stay fixed. Do not set it yourself. Kubernetes does not stop controllers with
overlapping selectors from overlapping, so they can conflict.

## Gotchas
- Fixing a typo in `selector.matchLabels` on a running Deployment is not possible by patch;
  plan a new Deployment.
- A Job manifest with a fixed name cannot be re-applied with a changed template once it
  exists; give each CI run its own Job name or delete the old Job first.
