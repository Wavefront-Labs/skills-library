# Skaffold: build, deploy and GitOps render

**Goal:** one client-side tool that owns the container workflow - build, tag, push, deploy - so the
inner loop and the CI/CD pipeline run the *same* configuration instead of two drifting scripts.

Skaffold is "client-side only. With no on-cluster component, there is no overhead or maintenance
burden to your cluster." All configuration lives in a single `skaffold.yaml`, generated by
`skaffold init` (answer the prompts, accept defaults, confirm the write). Profiles, local user
config, environment variables and flags vary it across environments.

## The inner loop: `skaffold dev`
```bash
skaffold dev
```
Builds and deploys, then watches: on a file edit it "intelligently sync[s] only the file you
changed" - the hot-reload path. Exiting with `Ctrl+C` **cleans up all deployed artifacts and ends
dev mode**, which makes it safe to point at a shared cluster for a quick check.

## The pipeline split: build / test / deploy
The commands that matter for CI are separable, passing state through JSON artifact files:

```bash
export STATE=$(git rev-list -1 HEAD --abbrev-commit)

# CI: build, tag, push
skaffold build --file-output build-$STATE.json

# CI: test the images that were built
skaffold test --build-artifacts build-$STATE.json

# CD: hydrate manifests with the built tags and deploy
skaffold deploy -a build-$STATE.json
```
`deploy` "hydrates your Kubernetes manifest with the image you built and tagged" - the tag
coordination (which image goes in which manifest) is the bookkeeping Skaffold removes.

## The GitOps split: render / apply
```bash
skaffold render -a build-$STATE.json --output render.yaml --digest-source local
skaffold apply render.yaml
```
`render` writes the hydrated manifest to a file instead of deploying; `apply` deploys a rendered
file. That is the GitOps shape: CI commits `render.yaml` to the config repo, and the delivery side
applies exactly what was built and reviewed - no tag drift between what CI tested and what shipped.

The `test:` section of `skaffold.yaml` runs per-image commands against built artifacts:

```yaml
test:
- image: skaffold-buildpacks-node
  custom:
    - command: echo This is a custom test commmand!
```

## Local cluster setup
The documented quickstart pattern uses minikube's Docker daemon so no image registry is needed:

```bash
minikube start --profile custom
skaffold config set --global local-cluster true
eval $(minikube -p custom docker-env)
```
On other local clusters, images need a registry or a side-load (see the
`kind-and-minikube-local-and-ci-clusters` skill for `kind load docker-image`).

## Builder and deployer variety
The plugin architecture covers Docker builds including Kaniko, and deploys via Helm or Kustomize -
the exact `skaffold.yaml` schema for each (`build.artifacts` with per-builder fields,
`deploy` with kubectl/helm/kustomize sections, image tagging policies, port-forwarding config)
lives in the YAML reference; confirm field names there for your builder rather than copying from
memory or examples.

## Choosing versus Tilt
Skaffold and Tilt overlap on the inner loop. The differentiator is the pipeline: Skaffold's
build/render/apply split is a natural CI/CD and GitOps entry point ("a common entry point across
applications that we can also reuse for CI/CD"), while Tilt's `live_update` in-place updates are
the tighter dev feedback. They can also be combined - Tilt driving the loop, Skaffold the pipeline.

## Failure modes
- **Deployed resources never cleaned up** - `skaffold dev` was killed instead of exited with
  `Ctrl+C`; its cleanup is not a signal handler you can skip.
- **Tag drift between CI and production** - deploying directly instead of through
  `render`/`apply`, so what runs is not what `test` validated.
- **Custom tests never run in CI** - the `test:` section exists but CI calls only
  `skaffold build` and `deploy`, skipping `skaffold test --build-artifacts`.
- **Images unresolvable on a local cluster** - built to the local daemon but the cluster pulls from
  elsewhere; use the minikube docker-env pattern, a local registry, or side-load.
- **Config drift per environment** - environment differences handled by editing
  `skaffold.yaml` copies instead of profiles.

## Verify
- [ ] `skaffold init` generates a config that `skaffold dev` runs end-to-end on a local cluster.
- [ ] A file edit triggers a sync, not a full rebuild, for an interpreted service.
- [ ] CI runs `build --file-output` -> `test --build-artifacts` -> (render or) `deploy -a`, in that
      order, with the artifact file passed between stages.
- [ ] The rendered manifest contains the digest of the image CI actually tested.
- [ ] `Ctrl+C` on `skaffold dev` removes everything it created.
