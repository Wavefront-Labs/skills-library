# Runtime threat detection and syscall sandboxing — detect vs. prevent

**Goal:** know the difference between a control that **blocks** a dangerous
syscall before it executes (seccomp, AppArmor) and one that **observes and
alerts** after it already ran (Falco) — most clusters need both, and conflating
them leads to thinking an alert is a block. Admission-time policy
(ValidatingAdmissionPolicy/Kyverno/Gatekeeper) prevents bad *configuration* from
being deployed; this skill is about what happens once a container is already
running and doing something unexpected.

## 1. seccomp — a per-syscall allowlist/denylist, enforced by the kernel
```yaml
spec:
  securityContext:
    seccompProfile: {type: RuntimeDefault}   # the container runtime's default profile (defined by the runtime; can differ between runtimes and versions)
  containers:
  - securityContext:
      seccompProfile: {type: Localhost, localhostProfile: profiles/custom-app.json}
```
- `RuntimeDefault` is the pragmatic baseline — required (as `RuntimeDefault` or
  `Localhost`) by the `restricted` Pod Security Standard and switchable node-wide with the kubelet
  `--seccomp-default` option (stable since v1.27); some workloads still need a looser profile, so
  test first.
- `Localhost` with a custom JSON profile (generated by recording the actual
  workload, see `seccomp-profile-generation-with-spo-and-inspektor-gadget`) gives a tighter allowlist specific to that app — real security gain,
  but it is **brittle**: a code path triggered rarely (an error-handling branch,
  a dependency upgrade that calls a new syscall) can suddenly make the
  workload fail in production if the profile wasn't generated against full
  coverage. Generate custom profiles from load-tested, not just happy-path,
  traffic, and re-validate after any dependency bump.
- A profile with `defaultAction: SCMP_ACT_ERRNO` makes denied syscalls fail with an error the
  application may not handle; start with `SCMP_ACT_LOG`, which records the syscalls a profile would
  deny in the node's syslog (Kubernetes seccomp tutorial), and switch once the log is quiet.

## 2. AppArmor — path and capability-scoped, not syscall-numbered
AppArmor profiles restrict file paths, network access, and capabilities by
name/pattern rather than raw syscall numbers — more human-readable than a
seccomp JSON profile, but **requires the profile to already be loaded on every
node** (`apparmor_parser` at node provisioning, or via a DaemonSet) before a pod
referencing it can start; the kubelet rejects a pod whose `Localhost` profile is not loaded
on the node it was scheduled to, because the scheduler does not know which profiles each node has
(Kubernetes AppArmor tutorial). The profile is set with `appArmorProfile` in the security context
(v1.30 and later; earlier releases used annotations). `RuntimeDefault` seccomp needs no per-node
profile loading, but `Localhost` seccomp profiles do need their file on every node.

## 3. Falco — syscall-stream detection, not prevention
Falco taps the kernel's syscall stream (via the modern eBPF probe, the default driver, or the
kernel module) and
evaluates rules against the live stream — it **cannot block** anything by
itself; by the time a Falco rule fires, the syscall already executed. Its value
is detecting the *behavior* a static policy couldn't anticipate: a shell
spawned inside a container that should never spawn a shell, a write to
`/etc/shadow`, an outbound connection to a non-allowlisted IP from a pod that's
never made one before.
```yaml
# simplified from the shipped rule of the same name (NOTICE priority, also requires
# container_entrypoint and has exception conditions)
- rule: Terminal shell in container
  desc: A shell was spawned by a container
  condition: spawned_process and container and shell_procs and proc.tty != 0
  output: "Shell spawned in container (user=%user.name container=%container.name command=%proc.cmdline)"
  priority: WARNING
```
- Default rule sets are a starting point, not a finished detection program —
  tune them against your own normal baseline (a sidecar that legitimately
  execs into tooling will trip "shell spawned" constantly if not excluded) or
  the signal-to-noise ratio collapses and the alerts get ignored.
- Falco output needs a **response pipeline** (Falcosidekick → Slack/PagerDuty/
  Falco Talon for response actions) — a Falco
  alert that only writes to a log nobody tails is equivalent to not having
  detection at all.

## 4. The combination that actually works
- seccomp/AppArmor as the **prevention** layer: deployed everywhere as a baseline
  (`RuntimeDefault`, via the kubelet default or Pod Security `restricted`), with custom profiles on
  the highest-value/highest-exposure workloads.
- Falco as the **detection** layer for everything the prevention layer either
  can't express (complex multi-step behavior, "this process shouldn't talk to
  this IP") or chose not to block (because a tight custom seccomp profile on
  every workload isn't operationally sustainable at scale).
- Neither replaces the other: a seccomp profile that's too permissive (because
  it was generated loosely to avoid breaking the app) still leaves room for
  exactly the kind of anomalous-but-technically-allowed behavior Falco is
  positioned to catch.

## Gotchas
- Falco's drivers are the modern eBPF probe (default; CO-RE, needs a kernel exposing BTF and the
  BPF ring buffer, usually 5.8 or newer) and the kernel module (needs full privileges and a
  module built for the node kernel). Check the driver requirements against every node image you run.
- Generating a custom seccomp profile from a short observation window captures
  only the syscalls exercised during that window — profiles built from a few
  minutes of smoke-testing commonly break under real traffic's less common
  code paths weeks later; treat profile generation as an ongoing process tied
  to load testing, not a one-time capture.
- Falco alerting on *every* container start event or routine administrative
  exec (a legitimate `kubectl exec` for debugging) without exclusions trains
  responders to ignore the channel — scope rules to genuinely anomalous
  patterns, and give legitimate operational exec sessions a quieter, separate
  audit trail instead (see `kubernetes-audit-logging`).

## Verify
- [ ] `seccompProfile: RuntimeDefault` is the enforced baseline cluster-wide
      (kubelet `--seccomp-default` or the `restricted` Pod Security Standard), not opt-in per team.
- [ ] Custom seccomp/AppArmor profiles for high-value workloads were generated
      against load-tested traffic and re-validated after the last dependency
      bump, not a one-time capture.
- [ ] Falco's driver matches every node image: the modern eBPF probe where the kernel exposes
      BTF and the BPF ring buffer, otherwise the kernel module built for that kernel.
- [ ] Falco alerts route to an actual response pipeline (paging/ticketing), not
      a log nobody reads; default rules have been tuned against the cluster's
      real baseline to avoid alert fatigue.
- [ ] A deliberate test (spawn a shell in a container that shouldn't, in a
      non-prod cluster) confirms both the seccomp/AppArmor block (if
      applicable) and the Falco alert actually fire.
