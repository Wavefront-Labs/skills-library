# Supply-chain security — proving what's in an image and how it was built

**Goal:** answer two distinct questions an incident or an auditor will ask —
"what's actually inside this image" (SBOM) and "was this built by the pipeline
we trust, from the source we expect, untampered" (provenance) — and make both
checkable at deploy time, not just filed away as a compliance artifact nobody
reads. Signing the image itself (identity) is in
`computing-software.cloud-infrastructure-engineering.kubernetes.container-image-signing-and-verification`;
CVE scanning of what the SBOM reveals is in
`computing-software.cloud-infrastructure-engineering.kubernetes.container-image-scanning-and-admission-gates`.

## 1. SBOM — inventory, not a security verdict
A Software Bill of Materials lists every package/library/version inside an
image. It does not say any of them are vulnerable or safe — it's the *input*
scanners consume (a scanner that enumerates packages itself is implicitly
generating an ephemeral SBOM; a separately generated SBOM lets you re-scan
later against updated CVE feeds without re-pulling and re-analyzing the image).
```bash
syft registry.example.com/app:1.2.3 -o spdx-json > app.spdx.json
syft registry.example.com/app:1.2.3 -o cyclonedx-json > app.cdx.json
```
- **SPDX** and **CycloneDX** are the two common formats (Syft can emit both). Pick one as your org standard —
  supporting both for every image doubles generation/storage cost for little
  benefit unless a specific downstream consumer requires the other.
- Generate at **build time**, not by scanning the pushed artifact later —
  build-time generation can see source-level dependency manifests (lockfiles)
  that a post-hoc image scan sometimes can't fully reconstruct (e.g. dev
  dependencies stripped from the final layer, or static-linked binaries that
  obscure what went into them).

## 2. SLSA provenance — did the pipeline you trust actually build this
SLSA (Supply-chain Levels for Software Artifacts) defines build levels. The current Build track has
L1 to L3 (the draft v1.3 adds L4). Roughly:
- **Level 1** — a provenance document exists (self-reported, no real guarantee).
- **Level 2** — provenance is generated by a build *service* (not a developer's
  laptop or a mutable self-hosted runner), authenticated, tamper-resistant in
  transit.
- **Level 3** — the build runs in a hardened, isolated build platform that
  prevents the build from tampering with its own provenance (for example
  `slsa-github-generator`, which documents Build L3 provenance for GitHub Actions) — provenance at this level is meaningfully harder to
  forge than a build script just writing a JSON file and signing it.
Provenance answers "which commit, which workflow, which builder produced this
exact digest" — it's what lets you refuse an image that *is* correctly signed
(proving an authorized identity's cert signed it) but was built from the wrong
source ref or a tampered build definition.

## 3. Attestations — SBOM and provenance attached to the artifact, signed
```bash
cosign attest --predicate app.spdx.json --type spdxjson registry.example.com/app@sha256:<digest>
cosign verify-attestation --type spdxjson \
  --certificate-identity-regexp '^https://github.com/org/repo/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.example.com/app@sha256:<digest>
```
An attestation is a signed statement (in-toto format) binding a predicate (the
SBOM, the SLSA provenance, a scan result) to the image digest — same
cosign/Sigstore trust chain as image signing itself, so it inherits that
skill's keyless/Rekor mechanics. Kyverno/policy-controller can require specific
attestation types exist and assert on their *content* (e.g. "SLSA provenance
predicate's `runDetails.builder.id` matches our known CI, and `buildDefinition.buildType` matches our
expected workflow (SLSA v1 field names)") before admitting the image — this is the actual enforcement
point; generating SBOMs/provenance that nothing ever checks is compliance
theater.

## 4. SBOM/provenance drift from what's actually deployed
- An SBOM generated at build time describes the image *as built*. If anything
  mutates the running artifact after that — a mutating admission webhook
  injecting a sidecar, a base-image hot-patch applied out of band — the SBOM no
  longer fully describes what's running. Prefer immutable, fully-built images
  over post-deploy patching specifically so the SBOM stays accurate.
- Re-scanning for CVEs against an SBOM is only as fresh as when it was
  generated — pair SBOM-based vulnerability tracking with the registry's
  continuous re-scan (see the scanning skill) rather than treating a build-time
  SBOM scan as a one-time check.

## Gotchas
- An SBOM is only as complete as the generator's language-ecosystem support —
  Syft/similar tools have varying depth per ecosystem (check the generator's documented coverage) —
  spot-check SBOM completeness against a known dependency list for a new
  ecosystem before trusting it as exhaustive.
- "We have an SBOM" and "we require/verify SBOM attestations at admission" are
  different maturity levels — most orgs stop at generation-and-storage; the
  actual supply-chain control requires the admission-time verification step in
  §3, or the SBOM is just an artifact nobody consults until after an incident.
- SLSA level claims are only as strong as the weakest link that produced the
  provenance — a Level 3 builder consuming a Level 0 base image or an
  unverified third-party action inherits that base image/action's risk; check
  provenance recursively for critical base images, not just your own build step.

## Verify
- [ ] SBOMs are generated at build time, in a chosen standard format, and
      attached as a signed attestation to the image digest (not stored
      separately and disconnected from the artifact).
- [ ] Provenance is generated by a build service, not a developer workstation,
      and is itself signed/attested.
- [ ] At least one admission policy verifies attestation *content* (builder
      identity, source repo/ref), not merely that an attestation exists.
- [ ] A deliberately-mismatched provenance (wrong source ref) is confirmed
      rejected in a non-prod cluster.
- [ ] Critical base images' own SBOM/provenance (from the upstream vendor) is
      reviewed, not assumed inherited automatically.
