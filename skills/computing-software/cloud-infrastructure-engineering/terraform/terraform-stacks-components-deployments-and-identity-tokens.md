# Terraform Stacks: components, deployments, identity tokens

Stacks (HCP Terraform) split a configuration into components and deploy them across multiple environments, regions or accounts. The configuration is identical across deployments, customised by input variables; each deployment has an isolated state file.

## Files
| File | Purpose |
|---|---|
| `<NAME>.tfcomponent.hcl` | `component` blocks (each with a module `source` and `inputs`), `required_providers`, `provider`, `variable`, `output` |
| `<NAME>.tfdeploy.hcl` | `deployment`, `identity_token`, `store`, `deployment_group` |
| `.terraform.lock.hcl` | provider lock file, generated by `terraform stacks init` (`-upgrade` to refresh); a Stack cannot run without one |

## Components and providers
```hcl
# providers.tfcomponent.hcl
required_providers {
  aws = { source = "hashicorp/aws", version = "~> 5.7.0" }
}

variable "regions"        { type = set(string) }
variable "role_arn"       { type = string }
variable "identity_token" {
  type      = string
  ephemeral = true
}

provider "aws" "configurations" {
  for_each = var.regions
  config {
    region = each.value
    assume_role_with_web_identity {
      role_arn           = var.role_arn
      web_identity_token = var.identity_token
    }
  }
}
```
```hcl
# components.tfcomponent.hcl
component "s3" {
  for_each = var.regions
  source   = "./s3"
  inputs   = { region = each.value }
  providers = { aws = provider.aws.configurations[each.value] }
}
```
Providers in Stacks differ from root modules: modules used by components cannot declare their own providers, arguments go in a `config` block, the alias is the second label in the block header, and `for_each` is supported. Every provider used must also be in `required_providers`. Only certain providers and versions support deferred changes (for example Kubernetes provider 2.32.0 or later).

## Deployments and identity tokens
```hcl
# deployments.tfdeploy.hcl
identity_token "aws" {
  audience = ["aws.workload.identity"]
}

deployment "development" {
  inputs = {
    regions        = ["eu-west-1"]
    role_arn       = "<YOUR_ROLE_ARN>"
    identity_token = identity_token.aws.jwt
  }
}
```
Authentication has two options: the `identity_token` block (JWT for OIDC, recommended over static credentials) or the `store` block that reads an HCP Terraform variable set.

For OIDC, first create the trust relationship in the cloud provider. For AWS this is an IAM OIDC provider for `https://app.terraform.io` with client ID `aws.workload.identity`, and a role whose trust policy requires `app.terraform.io:aud` and a `app.terraform.io:sub` pattern such as `organization:<org>:project:<project>:stack:<stack>:*`. The pattern can be widened to an organisation or project, or restricted to specific deployments or operations. Each deployment then passes its own role ARN plus the token.

## Gotchas
- The Stacks beta syntax and file names changed at GA (`.tfcomponent.hcl`); follow the current docs and the "Update for general availability" guide.
- Limits: up to 20 deployments, 100 components and 10,000 resources per Stack. Stacks are not available on legacy HCP Terraform team plans.
- Run `terraform stacks init` (or `-upgrade` after changing provider versions) before deploying.

## Verify
- [ ] `terraform stacks validate` passes (checks local component and deployment configuration).
- [ ] Each deployment's plan in HCP Terraform shows its components per region with the intended role.
