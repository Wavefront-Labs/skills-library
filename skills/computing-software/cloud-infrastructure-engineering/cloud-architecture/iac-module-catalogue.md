# Infrastructure-as-code standards and module catalogue

## Standards
- Language and versions pinned (`required_version`, provider version constraints).
- State: remote backend with locking, one state per environment and component; no local state.
- Layout: `modules/` (reusable) vs `live/` or `stacks/` (composition per environment).
- Naming, tagging and encryption applied inside modules, not left to callers.
- Formatting (`terraform fmt`), validation, linting (tflint), security scan (Checkov, Trivy) in CI.

## Module design
1. **Boundary**: one module per meaningful building block (e.g. "private storage account with
   diagnostics and private endpoint"), not one per resource and not one per whole app.
2. **Inputs**: small required set; secure defaults; validation blocks for allowed values.
3. **Outputs**: IDs and connection info consumers need.
4. **Versioning**: semantic versions via git tags; breaking input changes = major bump; changelog.
5. **Registry**: private registry (Terraform Cloud/Enterprise, Artifactory, git refs) with docs
   generated by terraform-docs.
6. **Testing**: `terraform test` / Terratest that deploys an example and asserts; run nightly.
7. Consider starting from vendor-curated modules (Azure Verified Modules, terraform-aws-modules)
   and wrapping them with org defaults.

## Gotchas
- Pinning consumers to `main`; any change breaks everyone. Pin versions.
- Wrapper modules exposing every upstream variable - no value added.
- Modules that create providers internally break `for_each` and multi-region usage.

## Verify
- [ ] Each module has examples, tests, docs and a semver tag.
- [ ] Dashboard of module versions in use; laggards contacted.
