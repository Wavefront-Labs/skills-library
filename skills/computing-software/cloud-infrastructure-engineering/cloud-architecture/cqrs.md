# CQRS

Commands update data through a write model; queries return data from a read model that has no domain logic.

## Decide first
Per the Azure Architecture Center, CQRS fits when:
- many users change the same data concurrently and fine-grained commands reduce conflicts;
- the UI is task-based or the domain is complex;
- reads and writes need separate performance tuning, especially when reads far outnumber writes (the read model scales out; the write model runs on fewer instances);
- teams want to work on the write and read sides independently.

It may not suit simple domains or business rules, or where simple CRUD-style access is enough. Fowler's warning: for most systems CQRS adds risky complexity, it should apply to one bounded context rather than the whole system, and suitability is the minority case. If only some queries are demanding, a reporting database can offload them while the main system serves the rest.

## Commands and queries
- Commands represent business tasks ("Book hotel room"), not low-level updates ("Set ReservationStatus to Reserved"). Refinements the page lists: client-side validation to prevent obvious failures, server-side logic for races (for example a waiting list for the last room) and asynchronous processing through a queue.
- Queries never alter data; they return DTOs shaped for the view, with no domain logic.
- The write model has the full command stack (business logic, validation, aggregates); the read model has none.

## Two levels
1. **Separate models, one data store**: distinct read and write logic over a shared database.
2. **Separate models, separate stores**: scale each independently and use different technologies (for example a document store for reads and a relational store for writes). The read store can be a read-only replica or have its own schema, such as a materialized view.

With separate stores the write side usually publishes events that refresh the read side. Message brokers and databases usually cannot share one distributed transaction, so the page recommends the Transactional Outbox pattern to persist the state change and event atomically, with an idempotent read-model consumer to tolerate duplicate delivery.

## With event sourcing
The event store is the write model and source of truth; read models are materialized views built from events and can be regenerated by replaying history. Building views from long histories is costly, so the page advises periodic snapshots.

## Consistency and cost
- Separate stores mean the read side can lag and show stale data; detecting and handling users acting on stale data needs deliberate design.
- Messaging adds failures, duplicates and retries to handle.
- Scaffolding tools such as O/RM frameworks cannot generate CQRS code from a schema, so custom bridging code is needed.
- Each store means its own schema to maintain.

## Verify
- [ ] The case for CQRS (read/write asymmetry, conflicts, complex domain) is written down for this bounded context.
- [ ] Event publication is atomic with the state change and the consumer tolerates duplicates.
- [ ] How the UI behaves while the read model is stale is decided and tested.
