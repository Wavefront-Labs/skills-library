# Stream Analytics jobs — windows, time and streaming units

**Goal:** a streaming SQL job that aggregates events correctly by *event* time, survives late and
out-of-order data, and scales with partitions instead of falling behind.

## 1. Job skeleton
Inputs (for example Event Hubs, IoT Hub, Blob/ADLS) → query → outputs (for example Event Hubs, Cosmos DB, Power BI); see the Stream Analytics docs for the current list of each.
```bash
az stream-analytics job create -g rg-stream -n asa-telemetry -l uksouth --output-error-policy Drop \
  --out-of-order-policy Adjust --order-max-delay 10 --arrival-max-delay 5 --data-locale en-GB --compatibility-level 1.2
az stream-analytics job start -g rg-stream -n asa-telemetry --output-start-mode JobStartTime
```
Develop and test queries in VS Code (ASA extension) with local sample data; deploy via ARM/Bicep generated by the extension.

## 2. Windows
```sql
-- 5-minute averages per device by event time (tumbling = fixed, non-overlapping)
SELECT DeviceId, System.Timestamp() AS WindowEnd, AVG(Temperature) AS AvgTemp, COUNT(*) AS N
INTO [lake-out]
FROM [eh-in] TIMESTAMP BY EventTime PARTITION BY PartitionId
GROUP BY DeviceId, PartitionId, TumblingWindow(minute, 5)

-- alert when > 3 failures within any 1-minute span (sliding window)
SELECT DeviceId, COUNT(*) AS Fails INTO [alerts] FROM [eh-in] TIMESTAMP BY EventTime
WHERE Status = 'FAIL' GROUP BY DeviceId, SlidingWindow(minute, 1) HAVING COUNT(*) > 3
```
| Window | Use |
|---|---|
| `TumblingWindow` | fixed buckets (dashboards, lake aggregates) |
| `HoppingWindow(size, hop)` | overlapping moving averages (10 min every 1 min) |
| `SlidingWindow` | "N events within T" detection |
| `SessionWindow(timeout, max)` | user/device sessions separated by inactivity |
| Snapshot (no function: add `System.Timestamp()` to `GROUP BY`) | group events with identical timestamps |

## 3. Time handling
- `TIMESTAMP BY` uses the event's own (application) time; without it events are processed by arrival time.
- **Late arrival tolerance** (event time older than arrival by > N s) and **out-of-order tolerance** (within N s)
  with policy *Adjust* (clamp timestamp) or *Drop*. Bigger tolerance = more output latency.
- Early arrival is a fixed 5-minute tolerance (events arriving earlier than their event time by more than that are dropped); it cannot be configured.
- Adjusted events get a new `System.Timestamp()` but their event-time field is unchanged.

## 4. Scale with streaming units
- SU V2 is the recommended model (SU V1 is to be deprecated); valid values are 1/3, 2/3, 1, 2, 3 and so on, up to your quota. Start with 1 SU V2 for queries without `PARTITION BY`, then tune by watching the `SU % Utilization` metric under representative load.
- **Embarrassingly parallel** job: input partitions = output partitions, a partitioned query (compatibility level 1.2+: set the partition key as an input property; 1.0/1.1: `PARTITION BY PartitionId` in every step), an output that supports partitioning. Non-partitioned steps together scale to 1 SU V2; each partition of a partitioned step can add 1 SU V2.
- Power BI output does not support partitioning, so such a job is not embarrassingly parallel.

## Gotchas
- Bigger out-of-order or late-arrival tolerance means more output latency; *Drop* discards events outside the tolerance, *Adjust* rewrites their timestamp. Choose deliberately.
- Input partition count not matching output partition count means the job is not embarrassingly parallel.

## Verify
- [ ] Job running; `SU % Utilization` stays well below saturation under peak load.
- [ ] Late-event test (event with old timestamp) handled per policy.
- [ ] Output rows per window match an independent count from the raw capture for a sample hour.
