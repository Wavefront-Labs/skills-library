Linkerd automatically enables mutual TLS for TCP traffic between meshed pods, including the control plane's own traffic, since the control plane runs on the data plane as well.

How it works: the control plane contains a certificate authority called identity. It issues a TLS certificate to each data plane proxy, bound to the Kubernetes ServiceAccount of the pod. These certificates expire after 24 hours and are rotated automatically. Proxies use them to encrypt and authenticate TCP traffic with other proxies.

Traffic that can still be non-mTLS:

- traffic to or from non-meshed pods, such as Kubernetes health checks
- traffic on ports marked as skip ports, which bypass the proxy entirely

The docs say you can verify which traffic is mTLS'd in a variety of ways.

Operational concerns for production:

- The trust anchor generated by the default `linkerd install` CLI command expires after 365 days and must then be rotated manually, which is non-trivial. You can instead provide your own trust anchor and choose the expiry, for example 10 years.
- The default cluster issuer certificate and key also expire after a year and must be rotated before then. Automatic rotation can be set up with cert-manager.
- Clusters using multi-cluster communication must share a trust anchor, so the default install setup does not work and you must provide an explicit trust anchor.

Linkerd requires mTLS for meshed-to-meshed communication, but by default it accepts plaintext traffic from non-meshed sources. This can be disabled with authorization policies.
