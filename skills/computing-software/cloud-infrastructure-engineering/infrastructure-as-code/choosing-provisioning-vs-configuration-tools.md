# Choosing provisioning vs configuration tools

**Goal:** one tool owns each layer, the handoff between them is explicit, and nobody
runs `terraform apply` to change a config file or writes 400 lines of Ansible to create a VPC.

## 1. The layers
| Layer | Examples | Natural owner |
|---|---|---|
| Day 0: accounts, networks, IAM, managed services, VMs, clusters | VPC, subnets, RDS, EKS, load balancers | **Provisioning**: Terraform/OpenTofu, Pulumi, CloudFormation, Bicep, Crossplane |
| Day 1: what is *inside* a VM / what the app needs on a host | packages, users, config files, services, certs | **Configuration**: Ansible (agentless), or baked into images (Packer), or cloud-init for the minimum |
| Day 2: operational actions | patching, restarts, rotations, ad hoc fleet queries, incident runbooks | Ansible / controller jobs, or managed-service automation |
| Kubernetes workloads | Deployments, Helm charts | GitOps controllers (Argo CD/Flux); Terraform only for the cluster and bootstrapping the controller |
Declarative state-tracking tools (Terraform, Pulumi, CloudFormation) shine when the resource has a
lifecycle and dependencies the API knows about. Procedural-but-idempotent tools (Ansible) shine when
the target is a running system without a state API and tasks must be ordered and conditional.

## 2. Decision rules
- Does the cloud API own the object (it has an ID, can be diffed, destroyed)? → provisioning tool. Ansible *can* create an EC2 instance, but it has no state file to notice the drift or dependency graph to replace it safely.
- Is the target a host's filesystem/processes? → configuration tool. Terraform `remote-exec`/`local-exec` provisioners are explicitly "a last resort" in HashiCorp's docs: no idempotency, no diff, taints on failure.
- Can it be baked? If the host should be immutable, bake with Packer (which can call Ansible) and let the provisioning tool roll the image; keep runtime config to cloud-init/user-data of a few lines.
- Is it a one-off operational action (restart, failover, rotate)? → Ansible playbook, not a Terraform resource.
- Is the team one or many? Platform team provisions; app teams configure within guard rails. Give each its own repo and pipeline.

## 3. The handoff
Three sane ways to pass provisioned facts to configuration:
1. **Inventory from state/cloud**: Ansible `aws_ec2`/`azure_rm`/`gcp_compute` inventory plugins keyed on tags Terraform sets (`tags = { role = "web", env = "prod" }`), or `cloud.terraform.terraform_state` inventory plugin reading the state backend. Tags are the contract.
2. **Terraform outputs → Ansible vars**: `terraform output -json > tf.json` in the pipeline, `-e @tf.json`; or the `cloud.terraform.terraform_output` lookup/module.
3. **Trigger**: Terraform finishes → pipeline runs the Ansible job (or launches a controller job template via API / `ansible/ansible` provider's `ansible_playbook` resource for tightly coupled flows). Prefer pipeline orchestration over the provider; the provider re-runs on every plan unless carefully keyed.
Reverse direction (Ansible calling Terraform): `cloud.terraform.terraform` module for a self-service wrapper, with the state in a remote backend — acceptable for controller-driven workflows, awkward for day-to-day development.

## 4. Anti-patterns
- Terraform `null_resource` + `local-exec "ansible-playbook ..."`: runs at the wrong time, cannot be planned, breaks `terraform destroy` ordering.
- Ansible managing cloud resources that Terraform also manages: two sources of truth; one will "fix" the other's change every run.
- Config files generated by Terraform `templatefile` into user-data for a 200-line nginx config: unreviewable, changes replace instances.
- Pulumi/CDK program that shells out to SSH: same as the provisioner problem with more code.
- Crossplane/Kubernetes operators for everything: fine for platform teams already in GitOps; painful for teams without a cluster to host the controllers.

## 5. A reference split
```
infra/            Terraform: network, IAM, EKS, RDS, ASG with image id from Packer, tags {role, env, app}
images/           Packer + Ansible roles: hardened base, app runtime
config/           Ansible: dynamic inventory by tags, roles for day-1 config, playbooks for day-2 ops
gitops/           Argo CD apps for in-cluster workloads
```
Pipelines: `infra` plan/apply with policy checks → `images` build on base-role change → `config` check/apply on inventory change → `gitops` reconciles continuously.

## Gotchas
- "Just use one tool" ends with either a 2,000-line Terraform provisioner mess or Ansible playbooks that pretend to be a state machine. Two tools with a clean contract is simpler than one tool doing both badly.
- Tag/label naming is the integration surface; change it only with both repos updated in the same change window.
- Terraform replacing an instance invalidates Ansible-applied state; either bake the config into the image or let the config pipeline react to inventory changes (controller inventory sync + provisioning callbacks).
- Secrets cross the boundary too: Terraform writes them to a secrets manager, Ansible reads them with a lookup — never through outputs in plain text.

## Verify
- [ ] Each resource type in your estate has exactly one owning tool, written down in the repo README.
- [ ] Terraform state contains no `null_resource`/`local-exec` that runs configuration management; Ansible code contains no module creating resources Terraform also tracks.
- [ ] A fresh environment can be built by running the provisioning pipeline, then the configuration pipeline, with only tags/outputs as the link.
