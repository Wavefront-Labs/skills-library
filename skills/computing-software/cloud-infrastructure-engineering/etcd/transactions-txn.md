A transaction is an atomic If/Then/Else construct over the key-value store. A `TxnRequest` holds a list of `Compare` conditions (a conjunction), a `success` list of operations applied if all comparisons are true, and a `failure` list applied otherwise. Transactions protect keys from unintended concurrent updates and build compare-and-swap operations.

Compare fields: `result` (EQUAL, GREATER, LESS, NOT_EQUAL), `target` (VERSION, CREATE, MOD, VALUE), the `key`, and the value to compare (version, create_revision, mod_revision or value). A comparison can also check for the absence or presence of a key. Each comparison checks a single key.

Operations in the success and failure blocks (`RequestOp`) are Range, Put or DeleteRange. Puts must have unique keys and may not share keys with other Puts or Deletes; a DeleteRange may not share keys with any Puts or Deletes. Modifying the same key more than once in a transaction is forbidden.

The `TxnResponse` has `succeeded` (whether the comparisons were true) and `responses`, the results of the applied block. Do not interpret the header of an inner response; read the latest revision from the top-level header of the `TxnResponse`.

The store revision is incremented only once for the transaction, and all events generated by it have the same revision.

Limits: `--max-txn-ops` (default 128) is the maximum number of operations permitted in a transaction, and `--max-request-bytes` (default 1572864) is the maximum client request size the server accepts.
