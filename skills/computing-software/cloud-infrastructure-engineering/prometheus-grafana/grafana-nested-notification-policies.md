# Nested notification policies

Grafana's policy tree works like the Alertmanager route tree: an alert instance starts at the **default policy**, descends into the first child whose matchers all match, then keeps descending. Without "Continue matching subsequent sibling nodes", sibling evaluation stops at the first match.

## Structure
```
Default policy -> contact point: ops-email, group by [grafana_folder, alertname]
  severity = page (continue) -> incident-channel     (audit copy: must be FIRST)
  team = payments            -> payments-slack
    severity = page          -> payments-pagerduty   (override group wait 10s)
  team = platform            -> platform-slack
    namespace =~ kube-.*     -> platform-pagerduty
```
Order matters. With the `continue` route listed last, an alert labelled `team=payments, severity=page` stopped at the payments route and never reached the audit contact point (run on Grafana 13.2.4: only the payments receivers fired). Put routes that need `continue` before the sibling that would otherwise end matching, and `continue: true` only on those.

## Settings per policy
- Matchers: `=`, `!=`, `=~`, `!~` on alert labels (rule labels + query labels + `grafana_folder`, `alertname`; both `grafana_folder="Payments"` and `alertname` appeared on every alert).
- Contact point (inherits from parent if unset; the inheritance case was not run) (gated: unconfirmed, source is paywalled or blocked).
- Override grouping (`group_by`); `...` disables grouping (not run here) (gated: unconfirmed, source is paywalled or blocked).
- Override timings: group wait, group interval, repeat interval.
- Mute timings / active time intervals attached to this policy.
- Continue matching siblings.

## Preview
In the rule editor, "Preview routing" shows which policy and contact point the rule's labels reach (UI, not clicked here) (gated: unconfirmed, source is paywalled or blocked); use it whenever adding labels. Simplified routing (contact point chosen on the rule, API field `notification_settings.receiver`) bypasses the tree for that rule: a rule labelled `team=payments, severity=page` with `notification_settings.receiver: platform-email` reached only that contact point, through an autogenerated route with labels such as `__grafana_receiver__`.

## Provisioning
The entire tree is one resource (file `policies:`; `PUT /api/v1/provisioning/policies` replaces the whole tree, as does the file); partial edits from multiple sources conflict. Terraform `grafana_notification_policy` was not run (gated: unconfirmed, source is paywalled or blocked).

## Gotchas
- Alerts with no matching child go to the default policy (an alert with only `severity=warn` went to the root contact point); keep it pointing at a monitored destination.
- Matchers on labels that come from queries (e.g. `instance`) vary per alert instance; route on rule labels (`team`, `severity`) instead.
