# YSQL authentication and host-based rules

Enable authentication on manually deployed universes by starting yb-tserver with `--ysql_enable_auth=true` (or add it to tserver.conf). With yugabyted, `yugabyted start --secure` enables it along with encryption in transit and writes the credentials to a file; `--ysql_enable_auth=true` also works. Enabling authentication enables authorization and RBAC automatically. Once enabled, every user, including `yugabyte`, needs a password. Outside a yugabyted secure universe the default `yugabyte` user has the password `yugabyte`.

Host-based authentication is set with the YB-TServer flag `--ysql_hba_conf_csv`, which works like `pg_hba.conf`. The default `listen_addresses` accepts only localhost connections, so remote access needs records here. The records are written to the autogenerated `ysql_hba.conf` (do not edit it by hand; edits are overwritten). Record formats: `local`, `host`, `hostssl` and `hostnossl`, each with database, user, address and auth-method fields plus optional auth-options. YugabyteDB searches records in order until the first one matching connection type, address, database and user, and authenticates on it; if authentication fails, later records are not tried. Put tight match rules before loose ones.

The flag is read at start-up, so changes need a restart of the yb-tserver processes, applied as a rolling restart so all tservers are never stopped together.

For password authentication use `scram-sha-256` (the default); `md5` is deprecated.

Examples:
- `host all yugabyte 127.0.0.1/0 trust, host all all 0.0.0.0/0 scram-sha-256, host all yugabyte ::1/128 trust, host all all ::0/0 scram-sha-256`
- `hostssl all all all scram-sha-256 clientcert=verify-full` requires a valid client certificate; `clientcert=verify-ca` verifies the certificate against the CA without using it for authentication
- `hostssl mydb myuser myhost cert,hostssl all all all reject`: the `reject` rule disables the autogenerated rules for non-matching connections

Test before you lock yourself out:
- `SHOW hba_file;` shows the file in use.
- `SELECT * FROM pg_hba_file_rules;` shows how the rules parse; non-null error fields point to bad lines.
- A user must pass the hba rules and also hold the `CONNECT` privilege on the database; granting or revoking `CONNECT` is usually easier than encoding it in hba rules.
- `local` connections need the full socket path: get it from the tserver log line "listening on Unix socket" and run `ysqlsh -h /tmp/.yb.127.0.0.1:5433`.
