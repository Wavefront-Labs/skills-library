# ORM migration frameworks (Alembic / Django / Rails / Prisma)

## Common workflow
Model change → autogenerate migration → **review the SQL** → test → apply in deploy. The generator is a starting point, not a DBA.

## Alembic (SQLAlchemy)
```bash
alembic revision --autogenerate -m "add orders.status"
alembic upgrade head --sql > review.sql        # offline SQL for review
alembic upgrade head
alembic downgrade -1
alembic merge -m "merge heads" <rev1> <rev2>   # resolve parallel branches
```
Autogenerate misses or misreads: column renames (seen as drop+add: data loss), server defaults, some type changes, constraints without names. Name constraints via `MetaData(naming_convention=...)`. Use `op.create_index(..., postgresql_concurrently=True)` inside `with op.get_context().autocommit_block():`.

## Django
```bash
python manage.py makemigrations
python manage.py sqlmigrate orders 0042      # see SQL
python manage.py migrate
python manage.py migrate orders 0041         # roll back
```
- `RunPython` for data migrations with a reverse function; use `apps.get_model` (historical models), not direct imports.
- `AddIndexConcurrently` (from `django.contrib.postgres.operations`) with `atomic = False` on the migration.
- `SeparateDatabaseAndState` to decouple state changes from DDL (e.g. renaming models without table renames).
- Squash long histories (`squashmigrations`).

## Rails
```bash
bin/rails generate migration AddStatusToOrders status:string
bin/rails db:migrate
bin/rails db:rollback STEP=1
```
`disable_ddl_transaction!` + `add_index :orders, :status, algorithm: :concurrently`. The `strong_migrations` gem blocks unsafe operations with guidance. `schema.rb`/`structure.sql` is the canonical snapshot (use `structure.sql` for DB-specific features).

## Prisma
```bash
npx prisma migrate dev --name add_status       # dev: generates SQL under prisma/migrations
npx prisma migrate deploy                      # prod: applies pending migrations only
npx prisma migrate diff --from-url $PROD --to-schema-datamodel prisma/schema.prisma --script
```
Generated SQL files can and should be edited before committing (add `CONCURRENTLY`, batching). `migrate dev` may reset dev databases on drift; never point it at production.

## Rules for all
- One migration per deploy step; expand/contract for renames and type changes.
- Keep data backfills out of the schema migration transaction (batch jobs).
- Set `lock_timeout`/`statement_timeout` in migration sessions.
- Never edit applied migrations; add new ones.

## Verify
CI applies migrations from scratch and on a snapshot; the generated SQL for each migration is attached to the PR and reviewed for locks and data loss.
