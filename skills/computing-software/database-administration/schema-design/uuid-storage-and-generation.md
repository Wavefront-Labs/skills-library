# UUID storage and generation

## Why UUIDs
Globally unique without a central sequence: IDs generated by clients/services, merge of data
from several databases, no guessable sequential ids in URLs. Cost: 16 bytes vs 8 for bigint,
and with random UUIDs, poor index locality.

## Version matters: v4 vs v7
- **UUIDv4** is random: each insert lands on a random B-tree page. With large tables this means
  page splits, a working set equal to the whole index, more WAL/redo (full page writes), and in
  clustered-index engines (InnoDB, SQL Server clustered PK) fragmentation of the table itself.
- **UUIDv7** (RFC 9562, 2024) starts with a 48-bit big-endian millisecond Unix timestamp (bits 0 to 47): inserts append near the
  right edge like a sequence, while staying globally unique. Prefer v7 for primary keys.
  It does reveal creation time.

## Storage per engine
| Engine | Type | Notes |
|---|---|---|
| PostgreSQL | `uuid` (16 bytes) | `gen_random_uuid()` (v4, added to core in 13); `uuidv7()` is in the PostgreSQL 18 manual (checked: returns 16 bytes, version nibble 7); extensions or app-side before that |
| MySQL | `BINARY(16)` | `UUID_TO_BIN(uuid, 1)` swaps the time-low and time-high groups and helps only for version 1 UUIDs (MySQL manual; use the same flag in `BIN_TO_UUID`); generate v7 in the app; never `CHAR(36)` |
| SQL Server | `uniqueidentifier` | `NEWSEQUENTIALID()` (default constraint only) for ordered values; SQL Server sorts uniqueidentifier by the **last** byte groups first (gated: unconfirmed, source is paywalled or blocked) |
| Oracle | `RAW(16)` | `SYS_GUID()` (gated: unconfirmed, source is paywalled or blocked) |
| SQLite | `BLOB` (16) | or TEXT if interoperability beats size |
Storing as `varchar(36)`: 36+ bytes, slower comparisons, collation overhead, and case/format
inconsistency bugs. Avoid.

## Patterns
- Internal bigint identity PK + external UUID column (unique index) for public APIs: compact joins,
  non-guessable public ids.
- If UUID is the PK in InnoDB, every secondary index record contains the PK columns (MySQL manual): a 16-byte PK inflates all indexes.

## Gotchas
- Do not parse meaning from UUIDs other than v7's timestamp; never rely on v1 MAC addresses.
- Client-generated ids must still be validated (format, not reused); unique constraint remains the guard.
- Mixed versions in one column are fine for uniqueness but lose ordering benefits.

## Verify
Check insert throughput and index size on a test with 10M+ rows comparing v4 and v7; confirm the
column type is the native 16-byte form (`\d table`, `SHOW CREATE TABLE`).
