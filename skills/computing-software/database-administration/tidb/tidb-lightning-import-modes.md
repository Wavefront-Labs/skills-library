# Tidb lightning import modes

TiDB Lightning imports terabyte-scale data into TiDB, typically for the initial load.

Inputs: files exported by Dumpling, CSV, and Parquet files generated by Amazon Aurora, Apache Hive or Snowflake. Sources: local disk, Amazon S3, Google Cloud Storage.

Two modes, set by `backend`:
- Physical import mode (`local`): encodes data into key-value pairs in a local temporary directory, uploads them to TiKV nodes and calls the TiKV Ingest interface to insert into RocksDB. Fast (100 to 500 GiB/hour), high CPU, disk and network use, not ACID during import, target tables must be empty, requires TiDB 4.0.0 or later, and the cluster offers only limited service during import.
- Logical import mode (`tidb`): encodes data as SQL statements and runs them. Slow (10 to 50 GiB/hour), low resource use, ACID compliant, target tables may already contain data, works with all TiDB versions and the cluster serves normally.

Rule of thumb from the docs: use physical for initial imports; use logical for production clusters or tables that already hold data. Actual speed depends on hardware, schema and index count.

The docs also note that the `IMPORT INTO` SQL statement runs directly on TiDB nodes with distributed task scheduling and TiDB Global Sort, and is described as significantly better in deployment, resource use, configuration, high availability and scalability.

Compatibility: physical import into tables that TiCDC is replicating is not supported.
