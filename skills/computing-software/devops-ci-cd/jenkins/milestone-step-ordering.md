# milestone ordering

## Semantics
The milestone step forces builds through in order (builds are ordered by build number). Per the step reference:
- An older build is aborted if it reaches a milestone that a newer build already passed.
- When a build passes a milestone, any older build that passed the previous milestone but not this one is aborted.
- Once a build passes a milestone it is never aborted by a newer build that has not passed it yet.

## Classic deploy pipeline
```groovy
pipeline {
  agent none
  stages {
    stage('Build')  { agent { label 'linux' }; steps { milestone(1); sh 'make build test' } }
    stage('Approve') {
      steps {
        milestone(2)
        timeout(time: 2, unit: 'HOURS') { input 'Deploy?' }
        milestone(3)                 // approving an old build aborts it if a newer one was approved
      }
    }
    stage('Deploy') {
      steps {
        milestone(4)
        node('deploy') { sh './deploy.sh' }
      }
    }
  }
}
```
- A milestone placed **after** `input` means that when a newer build is approved and passes it, older builds still waiting at the prompt (they passed the earlier milestone but not this one) are aborted.
- The plugin docs suggest combining `milestone` with the `lock` step for a reliable delivery pipeline; see the Lockable Resources docs for lock syntax.
- Ordinals are optional and autogenerated. Set explicit ordinals if you add or remove milestone steps while builds are running, so each milestone keeps the same identity across builds. The step also takes an optional `label`.

## Abort previous builds on new commit (PR jobs)
```groovy
def buildNumber = env.BUILD_NUMBER as int
if (buildNumber > 1) milestone(buildNumber - 1)
milestone(buildNumber)
```
Run at the very start (scripted / `script {}`); each new build passes milestone N, which
cancels the previous running build. Newer Jenkins core alternative:
`options { disableConcurrentBuilds(abortPrevious: true) }`, which aborts the running build when a new one starts.

## Gotchas
- Replayed or rebuilt old builds get a new, higher build number, so they win; be careful "rebuilding" an old commit to production.

## Verify
Start build 10, then 11; approve 11 first, then try 10: build 10 is aborted.
