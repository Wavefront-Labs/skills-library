`inheritConfig` lets an administrator define organisation-level defaults in a repository. When enabled, Renovate looks for the file named by `inheritConfigFileName` in the repository named by `inheritConfigRepoName` before processing each repository, and reads it as config.

For nested namespaces such as GitLab `topGroup/nestedGroup/projectName`, it looks in `topGroup/nestedGroup/renovate-config`.

```json
{
  "inheritConfig": true,
  "inheritConfigRepoName": "my-org/renovate-config",
  "inheritConfigFileName": "org-inherited-config.json",
  "inheritConfigStrict": false
}
```

Behaviour:

- If `inheritConfig` is true but the file does not exist, Renovate continues with no warning (only a debug log message). With `inheritConfigStrict=true` it aborts the run and raises a config error instead; only set that if every organisation has an inherited config file.
- If the file exists but cannot be parsed, Renovate raises a config warning issue and aborts the job.
- The inherited config may include all valid repository config plus a documented set of extra options, so organisations can control things like whether config is required and how repositories are onboarded.
- Inherited `hostRules` are treated as repository configuration for precedence and for whether `internalHostAccess` can be configured. By default they cannot grant access to internal hosts.
- `inheritConfigFileName` may be a nested path such as `some-dir/config.json`.
- `inheritConfigRepoName` must be on the same platform and endpoint, and Renovate's token needs `read` permission to it.
- Only set `inheritConfigTrusted` to `true` if everyone who can push to the `inheritConfigRepoName` repositories is trusted. The trust is transitive: `hostRules` in any preset the inherited config extends are trusted at the same level. On a multi-tenant platform leave it disabled.

The docs say `inheritConfig` is disabled in the Mend Renovate App, because each 404 for a missing org config costs a GitHub API call.
