# Writing task scenarios

A task scenario is the instruction a participant reads: a goal in a realistic situation, without telling them how.

## Rules
- **Start from user goals:** list what every user must be able to do, and write tasks from that list.
- **Wrap it in context:** a short scenario explaining the action and why the user is doing it, so participants behave as with a real need.
- **Keep it realistic:** do not ask for things participants would not normally do; match participants to the features tested.
- **Make it actionable:** ask participants to do the action, not to explain how they would do it (what people say is less accurate than what they do).
- **No clues:** do not name menu items, button labels or steps. Avoid interface wording, but use the established term when a standard name exists. Do not be vague either: supply everything needed without saying where to click.
- **Invented specifics are fine** (a named dentist, exact dates); users suspend disbelief. In paper or early prototypes you may need to ask participants to play a role.
- **Final check:** each task is realistic and typical, encourages interaction with the interface, and does not give away the answer.
- **Define success in advance:** decide what counts as a correct completion; the share of tasks completed correctly is a usability metric.

## Format
A table: task ID, scenario text, start state, success criteria, notes for the facilitator.

## Verify
- [ ] No scenario contains interface labels or steps.
- [ ] Each has an end state an observer can recognise.
