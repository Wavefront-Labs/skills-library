# Node-based scenario design

**Goal:** a scenario that survives players doing the unexpected, by building it as connected nodes rather than a railroad of scenes.

The approach is popularised by Justin Alexander's Node-Based Scenario Design series on The Alexandrian; this skill is a working summary.

## Procedure
1. **List the conclusions** players need (who, where, what is happening). See the three-clue-rule skill.
2. **Make a node for each place, person, or event** that can hold information: a witness, a crime scene, a library, a ledger. Each node is a self-contained, prepped situation with its own description, inhabitants and goal.
3. **Place clues in nodes** so each conclusion is pointed to by at least three clues, and each clue points to another node ("a delivery address", "a name", "a symbol").
4. **Draw the node map:** nodes as boxes, clue links as arrows. Check the map is connected from several starting points and has loops, not a single chain.
5. **Plan entry points** and a way to introduce further nodes if players run dry (a visit, an attack, an offer).
6. **During play,** run whichever node the players choose, record found clues, and update the map. Add new nodes when players invent leads.
7. **Prep the finale as a node too:** it may be reached early, so keep its content complete without relying on a fixed lead-in.

## Gotchas
- A chain with one link per node is a railroad; add redundancy.
- Nodes need action too, not only information; give each a problem or event.
- Over-prepping node text slows you down; prep bullet points and names.

## Verify
- [ ] Every conclusion has three or more clues across different nodes.
- [ ] Map has multiple entry points and no dead-end chain.
- [ ] Each node has an active element, not only data.
